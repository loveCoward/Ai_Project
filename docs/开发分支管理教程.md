# 开发分支管理教程

面向本仓库（`biddesk-zq`）的实际工作方式编写。日期：2026-11-04。适用环境：Windows + Git Bash + `uv` + 本地 PostgreSQL 18。

本教程只讲分支怎么用，不改变仓库既有的业务基线、测试要求和文档协作规则；这些以 `AGENTS.md` 为准。

## 1. 先建立心智模型

### 1.1 分支只是一个指针

Git 里真正的东西只有一种：**提交（commit）**。每个提交记录一份完整快照，并指向上一个提交，形成一条不可变的历史链。分支不是文件夹、不是副本，它只是一个**指向某个提交的名字**。

因此：

- 创建分支几乎不花时间和空间（写一个 41 字节的文件）
- 切换分支不是"复制文件"，而是"把工作区改成那个提交的样子"
- 删除分支只是删掉一个名字，提交本身还在（用 `reflog` 能找回来）

### 1.2 四层结构，命令各管一层

| 层 | 位置 | 相关命令 |
| --- | --- | --- |
| 工作区 | 你磁盘上看到的文件 | 编辑、`git add` |
| 暂存区 | `.git/index`，下次提交的内容 | `git add` / `git restore --staged` |
| 本地分支 | `.git/refs/heads/*`，只在你机器上 | `git commit` / `git switch` / `git branch` |
| 远程分支 | GitHub 上的 `origin/*` | `git push` / `git fetch` / `git pull` |

搞清楚这张表，80% 的困惑就消失了。`git status` 永远在告诉你前三层的差异，`git log` 告诉你看第四层。

### 1.3 一个常见误解

"切分支会不会把我的改动搞丢？"

不会。只要改动没被提交，它就一直待在**工作区**里，切到哪个分支它都跟着（除非目标分支那个文件内容不同、Git 拒绝切换）。真正会丢改动的操作只有两个：`git checkout -- <file>` 和 `git reset --hard`。这两个命令本章后面会单独讲。

## 2. 本仓库的现状

当前状态（截至 2026-11-04）：

- 主干只有 `main`，阶段一已提交为 `2910a1e`
- `main` 跟踪 `origin/main`，远端为 GitHub
- 阶段二A 的 2A-0 已在 `feat/phase-2a-0-auth` 分支上开发中，工作区有未提交改动
- CI 在 `.github/workflows/test.yml`

本地有一批**不会跟着分支走**的东西，这是本节的重点：

| 内容 | 是否跟分支走 | 说明 |
| --- | --- | --- |
| `src/` `tests/` `docs/` `migrations/` | 跟 | 版本控制内，切分支即切换 |
| `.venv/`（约 1 GB） | 不跟 | 被 `.gitignore` 忽略，全仓库共用一份 |
| `.env` | 不跟 | 本地配置，切分支后可能缺新配置项 |
| `privatecredentials/` | 不跟 | 本地秘密材料 |
| `checkpoints.db` | 不跟 | 本地运行产物 |
| 本地 PostgreSQL 实例与数据 | 不跟 | 数据库状态不在 Git 里 |

后果很直接：**切到分支后发现 `ModuleNotFoundError` 或配置项缺失，不是你写错了，是本地环境还停在旧分支的状态**。见第 6 节。

## 3. 一次完整的分支生命周期

以阶段二A 的 2A-0 为例，从切分支到合回 `main` 共 7 步。

### 第 1 步：出发前确认状态

```bash
git switch main
git status
git pull
```

`git status` 必须是干净（`nothing to commit, working tree clean`）才继续。如果当前分支还有没提交的改动，先看完第 7 节再决定是提交还是暂存。

`git pull` 必须先做，否则你是从旧的 `main` 切的，合并时会多出一堆无谓冲突。

### 第 2 步：创建并切换到新分支

```bash
git switch -c feat/presales-2a0-auth
```

一条命令同时完成"创建"和"切换"。等价的老写法是 `git checkout -b`，`switch` 是 2.23 之后的新命令，语义更清楚，推荐用新的。

验证：

```bash
git branch
```

带 `*` 的就是当前分支。

### 第 3 步：开发，边写边提交

不要攒到最后一次性提交。**提交是存档点**，写崩了可以回到上一个存档。

```bash
git add src/presales/api/ src/presales/asgi.py
git commit -m "2A-0: 增加售前独立路由，隔离脚手架入口"

git add tests/presales/test_auth.py
git commit -m "2A-0: 补充伪造主体与越权访问反例"
```

提交信息格式建议：`<阶段/范围>: <做了什么>`。第一行不超过 50 字，需要展开就空一行写正文。

同一个分支里允许有"修个 typo"这种碎提交——最后合并时会压成一个，不用担心难看。

### 第 4 步：自测，拿到证据

按 `AGENTS.md` 的要求，改动范围决定测试范围：

```bash
uv run pytest tests/presales/
uv run ruff check
uv run pyrefly check
```

涉及权限、来源过滤、状态转换的改动，必须跑对应专项测试并**记录真实输出**。测试没过的分支不要合并，哪怕只是"应该没问题"。

### 第 5 步：合并回 main

```bash
git switch main
git merge --squash feat/presales-2a0-auth
git commit -m "阶段2A-0：认证与入口隔离"
```

`--squash` 的语义是：把分支上所有提交的**最终结果**放到暂存区，但不产生合并提交、不保留分支历史。效果是 `main` 上只多出一个干净的提交。

为什么本仓库推荐 `--squash`：每个增量都要配一份验证记录和 `STATUS.md` 更新，一个增量对应一个可回滚的提交点，比十几个碎提交有用得多。

另外两种合并方式，知道区别即可：

| 方式 | 效果 | 适用 |
| --- | --- | --- |
| `git merge <branch>` | 保留分支历史 + 产生合并提交 | 多人协作，想看到完整脉络 |
| `git merge --no-ff <branch>` | 强制产生合并提交（即使能快进） | 想显式标记"这里合入了一个功能" |
| `git merge --squash <branch>` | 压成一个提交，不保留分支历史 | 单人、增量制、要求干净历史 |

### 第 6 步：推送

```bash
git push
```

推送前再 `git log --oneline -5` 确认一下，看有没有把不该提交的东西带上去。

### 第 7 步：删掉已完成的分支

```bash
git branch -d feat/presales-2a0-auth
```

`-d` 会检查分支是否已合并，安全。`-D` 是强制删除，只在"这个分支我彻底不要了"时用。

然后从最新的 `main` 切下一个分支：

```bash
git switch -c feat/presales-2a1-knowledge
```

**关键点：下一个分支必须从 `main` 切，不要从上一个分支切。** 否则 2A-1 会带着 2A-0 的历史，一旦 2A-0 需要返工，2A-1 也得跟着重建。

## 4. 必背命令表

日常 90% 的场景只需要这 12 条。

| 命令 | 作用 |
| --- | --- |
| `git status` | 看当前处于哪一层、有哪些改动（最常用，不确定就敲它） |
| `git branch` | 列出本地分支，`-a` 含远程，`-vv` 含跟踪关系 |
| `git switch <name>` | 切到已有分支 |
| `git switch -c <name>` | 创建并切换 |
| `git switch -` | 切回上一个分支（像 `cd -`） |
| `git add <path>` | 把改动放进暂存区；`git add -A` 全部 |
| `git commit -m "..."` | 提交暂存区 |
| `git log --oneline --graph -10` | 看最近 10 个提交和分叉形态 |
| `git diff` | 工作区 vs 暂存区；`git diff --staged` 暂存区 vs 上次提交 |
| `git merge --squash <branch>` | 把分支压成一个提交 |
| `git push` / `git pull` | 与远端同步 |
| `git branch -d <name>` | 删除已合并分支 |

补充三个诊断用：

```bash
git diff main...feat/presales-2a0-auth    # 本分支相对 main 的净差异
git show <commit>                          # 看某个提交改了什么
git reflog                                 # 看 HEAD 的完整移动历史（救命用）
```

## 5. 冲突怎么处理

### 5.1 什么时候会冲突

两个分支改了**同一个文件的同一区域**，Git 无法自动决定留哪个。

本仓库最容易冲突的三个位置：`STATUS.md`、`docs/` 下的方案文档、`migrations/versions/` 的编号。

### 5.2 冲突长什么样

合并时 Git 会停下并报 `CONFLICT`，文件里出现：

```text
<<<<<<< HEAD
当前分支的内容
=======
要合进来的分支的内容
>>>>>>> feat/presales-2a0-auth
```

### 5.3 处理步骤

```bash
git status                    # 会列出 "both modified" 的文件
# 用编辑器打开每个冲突文件，删掉标记行，留下你真正想要的内容
git add <解决完的文件>
git commit                    # squash 模式下是 git commit；普通 merge 用 git merge --continue
```

想整体放弃这次合并、回到干净状态：

```bash
git merge --abort
```

### 5.4 减少冲突的习惯

- 每个分支只碰一件事，不要"顺手改了点别的"
- 开始新分支前先 `git pull`
- 分支存活时间短（1-3 天内合掉），越长越容易冲突
- `STATUS.md` 这类共享文件放在分支最后一次提交里更新

## 6. 本项目的三个专属坑

### 6.1 切分支后依赖不对

`.venv` 不跟分支走。如果目标分支改了 `pyproject.toml` / `uv.lock`，切过去之后必须同步：

```bash
uv sync --frozen
```

遇到 `ModuleNotFoundError`，第一反应是"这个分支的依赖我同步了吗"，而不是去改代码。

### 6.2 切分支后配置缺项

`.env` 也不跟分支走。如果分支新增了配置项（比如阶段二A 的 JWT 密钥），本地 `.env` 不会自动多出来。做法是：

1. 看 `.env.example` 里新增了什么（它跟分支走）
2. 手工在本地 `.env` 补上对应值

同样的道理适用于 `privatecredentials/`。

### 6.3 切换分支后数据库和迁移不一致

本地 PostgreSQL 里是上一个分支的 schema。切到改动过迁移的分支后，先升级：

```bash
uv run alembic upgrade head
```

如果新分支删改了迁移文件，最干净的做法是丢掉临时库重跑。本仓库的集成测试用的是**独立临时回环实例**，不要对着长期保留的库做实验。

### 6.4 Windows 换行警告

切分支或 `git add` 时可能看到 `LF will be replaced by CRLF`。这是 Git 在 Windows 上的正常提示，不影响提交内容。**不要去改 `core.autocrlf` 来消掉它**，那会让整个仓库的 diff 变成全文件变更。

## 7. 后悔药

按"损失从小到大"排列，越往后越危险。

### 7.1 丢弃某个文件的未提交改动

```bash
git restore src/presales/api/app.py
```

只影响这一个文件，无法撤销。**先 `git diff <file>` 看一眼再执行。**

### 7.2 把改动从暂存区撤回工作区

```bash
git restore --staged src/presales/api/app.py
```

改动还在，只是不再准备提交。

### 7.3 修改刚才那个提交

```bash
git add 漏掉的文件
git commit --amend --no-edit
```

只适用于**还没 push** 的提交。已经 push 过的不要 amend，改用新的提交修正。

### 7.4 临时搁置改动去处理别的事

```bash
git stash push -m "2A-0 半成品"
git switch main
# ...处理完别的事
git switch feat/presales-2a0-auth
git stash pop
```

`git stash list` 查看所有搁置项。注意：`stash` 不包含未跟踪文件，新增文件需要 `git stash -u`。

### 7.5 回到某个历史提交（三种危险程度）

```bash
git reset --soft HEAD~1     # 撤销提交，改动留在暂存区
git reset HEAD~1            # 撤销提交，改动留在工作区（默认）
git reset --hard HEAD~1     # 撤销提交，改动直接删除 ← 唯一会真丢代码的
```

用 `--hard` 前先确认：`git status` 干净吗？`git stash` 备份了吗？拿不准就用 `--soft`。

### 7.6 撤销一个已经推送的提交

```bash
git revert <commit>
```

生成一个"反向提交"，历史往前走而不是倒退。这是公共分支上唯一正确的撤销方式。本仓库的 `main` 只有你一个人推，但保持这个习惯没坏处。

### 7.7 最后的救命稻草

```bash
git reflog
```

记录 HEAD 每一次移动，包括 reset 掉的提交。找到目标提交的哈希后：

```bash
git switch -c rescue <hash>
```

只要没被 Git 的垃圾回收清掉（默认 30 天），就还能捞回来。

## 8. 合并前的检查清单

每个分支合回 `main` 之前，逐条过一遍：

1. `git status` 干净，没有"顺手改了但忘了提交"的文件
2. `git diff main...HEAD` 的改动范围，全部属于这个分支该做的事
3. 与改动范围匹配的测试已跑过，输出是真实的、不是回忆的
4. 新增/变更的迁移文件编号连续，没有和别的分支撞号
5. `STATUS.md` 已按可核验事实更新（如果本增量改变了项目状态）
6. 没有把 `.env`、密钥、真实客户材料、`checkpoints.db` 之类带进提交

`git add -A` 之前永远先 `git status` 看一眼，这条能挡掉绝大多数事故。

## 9. 速查卡

```bash
# 开工
git switch main && git pull
git switch -c feat/<scope>-<desc>

# 干活
git status
git add <path> && git commit -m "范围: 做了什么"
uv run pytest <范围>

# 收工
git diff main...HEAD                  # 核对差异
git switch main
git merge --squash feat/<scope>-<desc>
git commit -m "阶段X：<增量名>"
git push
git branch -d feat/<scope>-<desc>

# 出事
git reflog                            # 先看这个
git stash                             # 想暂停又不想提交
git merge --abort                     # 想放弃这次合并
```

分支命名规则、type 取值和本仓库的建议清单，见对话记录中的说明；核心是 `<type>/<scope>-<desc>`，小写、短、不含中文、不用个人名和日期。
