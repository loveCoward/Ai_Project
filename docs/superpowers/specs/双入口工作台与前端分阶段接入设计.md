## 1. 结论与接入时机

建议在阶段二A内补入最小前端基础，阶段二B开始前完成；SSE 与真实的后台分析生命周期随二B共同实现，阶段三、四各自交付对应业务页面，阶段五负责体验收口、导出和整体运行验证。保持原阶段编号与滚动规划方式，不新增独立的大规模前端改造阶段。

理由：二A首次把认证、受限材料和知识能力开放给浏览器，此时验证登录、API 类型和错误处理成本较低；二B才开始分析尝试、取消和后台执行，适合一起确定任务启动、快照读取和进度订阅。等到阶段三再引入前端，会把前两阶段的接口和会话问题积累到审批联调时；等到阶段五则会同时暴露编辑、权限、恢复和部署问题。反之，在二A前完成全部页面会依赖尚未设计的二B至四契约，产生返工。

## 2. 已确认的方向与比较

| 方向 | 取舍 | 结论 |
| --- | --- | --- |
| React + TypeScript + Vite连接FastAPI | 增加Node构建、类型契约和浏览器集成测试；能逐阶段承载任务、表单、证据和审批页面，无须额外Node业务服务端 | 用户选择；作为核心工作台 |
| NiceGUI/Reflex等Python UI | 可减少直接编写TS，但仍要维护UI会话模型、业务API和恢复协议；不能自动解决业务持久化和授权 | 不作为本项目核心UI路线 |
| Next.js + CopilotKit/AG-UI | 有Agent交互组件，同时增加服务端/代理层；现有通用AG-UI不能替代售前业务协议 | 不作为首版基础；将来有明确聊天需求再评估 |

Streamlit继续承担脚手架联调、聊天演示和内部验证。React承担Opportunity、Presales Task、Evidence、Proposal Draft/Version、Review/Approval与发布恢复。两者不形成两套业务规则；Streamlit若访问售前对象，也必须调用相同业务API并使用真实业务身份。通用脚手架演示与售前数据/thread保持隔离。

2026-11-06，用户明确接受：任务和草稿状态在服务端持久化、后台分析脱离页面连接、重登后按当前权限继续；保留Streamlit并增加TS前端；REST提交业务操作、SSE推送进度、断线后读取当前业务快照；最终回复“我选择方案1”。这些确认不等于具体API、依赖版本、前端实现或产品验收已完成。

## 3. 状态与执行归属

- PostgreSQL业务记录保存任务、内容修订、审批及逐项发布结果。LangGraph checkpoint服务执行恢复；React内存、Streamlit session_state和SSE事件均不充当业务事实来源。
- 前端只保存当前导航、尚未提交的输入及可重取的查询缓存；“保存成功”以业务API回执为准。刷新不保证保留尚未提交的文字，后台业务恢复与未保存表单恢复须区分。
- 二B在后端以可信尝试记录管理执行寿命，不将LangGraph执行绑定到一次SSE响应、请求处理协程或浏览器连接。断线只结束订阅；取消必须是通过业务门禁的显式命令。首版仍遵守全局/单任务1个活跃分析，不因新增前端而引入队列服务或多人实时协同编辑。
- 浏览器重开不自动重启分析或恢复发布；先重新认证、读取当前状态，需要继续执行时按对应阶段的恢复规则发命令。进程重启不承诺无条件自动续跑，未知和在途结果仍先核实。

## 4. REST与SSE的边界

业务查询、保存、提交、审批、取消和恢复走REST；写命令绑定对象、预期修订和稳定请求身份，后端执行状态/权限/幂等检查。提交响应丢失后先按同一请求身份核实，不通过换键重试制造第二次操作。JSON Schema/OpenAPI与前端DTO保持一份契约来源，具体生成工具随实现选定，不手写第二份业务枚举作为独立事实。

SSE只传递经授权的业务进度投影。订阅绑定任务、尝试/版本及修订等必要身份；不原样转发完整graph state、Prompt、工具参数、秘密或未过滤证据。现有`src/service/agui.py`属于通用脚手架，不能直接开放给核心工作台承担审批或恢复，也不能将AG-UI的resume当作审批命令。

断线重连采用“重新鉴权、读取当前快照、继续订阅”的体验，不承诺补播所有临时token或旧进度事件。二B需设计并测试快照与订阅的交接：可先建立订阅并暂存事件再读快照，结合单调修订/游标去重，并在重连及终态时重新查询；也可采用有一致性保证的等效协议。不得留下读完快照、尚未订阅期间已完成却永远显示运行中的缺口。发布、审批等持久结果必须能通过API重新查询，事件丢失不能丢掉业务事实。

SSE长连接须在建立时及持续推送前复核当前身份/来源权限，并定义token到期和撤权后的终止处理。前端到期停止受保护订阅并清除受限查询缓存，重新登录后再读取；合法后台分析不单因浏览器token自然到期中止，仍遵守发起人的当前授权。浏览器已接收内容不能远程撤回，后续读取不得沿用旧权限。

## 5. 前端基础的工程默认值与成本

建议使用独立`frontend/`目录（2A-0已建立React 19/TypeScript/Vite 7最小工程），由Vite构建静态资源；开发时通过`/auth`、`/api`代理业务API，交付时由同源静态入口/反向代理连接FastAPI，不新增Node业务运行时。当前只引入React、React DOM与React Router；查询/组件库及同源生产接入仍随二A后续核定，只引入最小依赖。

认证沿用业务JWT；建议首版access token仅存在内存，不放URL或持久浏览器存储。刷新后允许重新登录；不得向浏览器暴露脚手架共享AUTH_SECRET或服务凭据。原生EventSource不能直接设置Authorization头，建议用支持Bearer头的fetch流式订阅；不把JWT拼到SSE URL。代理缓冲、超时、心跳和关闭行为要在二B原生环境验证，阶段五再覆盖Compose路径。

新增成本集中在TS/React学习、前端依赖与构建、DTO同步、浏览器认证/SSE调试和端到端验证。分阶段交付将这些成本先限制在一个可联调页面，再随业务扩展；没有实测依据时不把工时或框架生产力写成承诺。

二A前端工程退出检查至少包含类型检查、生产构建、登录/到期/越权和受限读取的真实API集成；二B增加断线、重连竞争、刷新与取消；三、四随业务增加修订冲突、审批和发布恢复用例。UI fixture只用于工程展示，必须标注，不能替代真实后端授权、持久化或模型能力证据。具体前端命令在工程建立后写入README与CI，当前不虚构可运行命令。
