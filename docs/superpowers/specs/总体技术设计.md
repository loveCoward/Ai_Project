### 3.2 TD-002：在现有仓库和服务基础上建设模块化售前后端

状态：设计方向已确认。确认日期：2026-11-02。

沿用适用的 FastAPI、模型适配、流式通信及持久化接入基础，逐步建设明确的售前业务模块和 Streamlit 工作台。两个本地 MCP Server 保持工具边界，并遵守与 API 一致的身份、数据范围和业务校验要求。

比较过的另一方案是在仓库内新建独立售前应用，再迁移组件：隔离更直接，但需重新组织启动、配置和客户端适配。选择沿用服务基础，以便渐进改造；不能为兼容旧接口而放宽已批准的权限或审批规则。

已确认的职责方向：

| 组成 | 负责的事项 | 后续必须明确的边界 |
| --- | --- | --- |
| FastAPI 业务层 | 身份、权限、业务状态转换、审批门禁和业务操作 | 入口统一校验、事务范围、并发与失效判断 |
| PostgreSQL 业务记录 | 任务、版本、批准清单和逐项发布结果的权威记录 | 表结构、约束、迁移及与执行状态的衔接 |
| LangGraph | 分析编排、节点执行、中断和恢复 | checkpoint 与业务记录的关联、重放和当前授权复核 |
| Streamlit | 任务、证据、草稿编辑、审阅、审批及恢复交互 | 页面分工、接口映射、状态与错误呈现 |
| Product Catalog MCP | 只读产品能力、版本、部署及集成限制 | 契约、来源、授权过滤和确定性模拟 |
| Opportunity Workspace MCP | 商机背景读取及精确批准后的外部业务写入 | 参数绑定、目标权限、幂等、核实和恢复 |

业务记录与图执行状态的职责分离已经确认；数据库布局见 TD-003。采用同一存储服务也不能推定不同连接下的业务写入、checkpoint 与 MCP 写入自动具有共同事务。

### 3.3 TD-003：单 PostgreSQL 实例、单数据库、按职责划分 schema

状态：设计方向已确认。确认日期：2026-11-02。对应 Round 2 Q3，用户回复“3) 同意”。

业务数据、知识数据和工作流数据共用一个 PostgreSQL 实例及数据库，按职责划分 schema，分别管理表、迁移和连接配置。schema 名称、数据库权限、连接池及当前 LangGraph 适配器的兼容性留待详细设计验证；不能把命名空间分组视为已落实的数据授权。

| 分组 | 数据职责 |
| --- | --- |
| 业务数据 | 任务、方案修订、审批、批准清单、逐项发布结果及受治理的业务记忆 |
| 知识数据 | 文档版本、解析块、向量、来源及适用性信息，支撑受限检索和证据定位 |
| 工作流数据 | LangGraph checkpoint 和中间执行状态，支撑节点执行、中断及恢复 |

比较过的另一方案是分离业务数据库与工作流数据库，便于独立维护，但增加首版本地演示的配置和恢复协调工作。首版采用共库分组。该选择不等于批准 PostgreSQL 的具体版本、安装位置或 Docker 部署方式，也不替代双 MCP 自身的确定性模拟存储设计。

业务批准已保存而图状态尚未推进时，恢复须核对既有批准、当前权限和目标修订；重复执行节点不能视为再次批准。共同数据库不自动消除跨连接或外部写入的一致性问题，具体幂等、核实和恢复协议在后续专题中设计。

### 3.4 TD-004：Windows 原生运行与可配置的本地文件目录

状态：设计方向已确认。确认日期：2026-11-02。Round 2 用户认可存储原则并说明 Windows 未安装 Docker；Round 3 用户对调整后的原生运行和本地目录方案回复“4) 同意”。

FastAPI、Streamlit 和两个本地 MCP 服务采用 Windows 本机进程运行，优先连接本机 PostgreSQL/PGVector。MCP 的通信方式及进程启动编排待细化。当前相关安装只做过文件存在性核查，服务、扩展启用及版本兼容性仍需验证。

文件内容与数据库中的身份、版本、校验值、来源和权限关联分开管理；文件读取经过后端授权，保留历史版本，结构化 JSON 内容快照作为 Markdown/HTML 的统一来源。采用可配置根目录的本地文件存储接口：Windows 原生运行时使用指定普通目录，容器运行时配置为挂载目录。数据库保存逻辑存储键与文件元数据，不将某台机器的绝对路径作为业务身份。开发运行目录不进入版本控制，也不直接作为公开静态资源目录。

文件根目录的具体路径、操作系统权限、原子写入、缺失和中断处理、数据库与文件一致性及清理规则待详细设计。原先要求 Windows 开发机使用 Docker 持久卷的建议已被本方案替代；本机 Docker 不是日常开发前提。

### 3.6 TD-006：按业务职责划分模块，由应用服务组织操作

状态：设计方向已确认。确认日期：2026-11-02。Round 4 Q6 用户回复“6) 同意”。

在同一个售前后端内划分以下职责模块；模块划分本身不增加微服务或独立部署单元。

| 模块 | 主要职责 |
| --- | --- |
| 身份与访问控制 | 登录身份、角色、对象授权、来源权限交集 |
| 商机与任务 | 商机上下文、本地任务、输入清单、任务状态 |
| 材料与知识 | 文件解析、知识版本、发布与停用、检索和证据定位 |
| 分析执行 | 分析尝试、LangGraph 编排、节点结果、取消与恢复 |
| 方案与审阅 | 草稿修订、方案快照、内容门禁、审阅及审批记录 |
| 发布与外部工具 | MCP 适配、批准动作集合、逐项执行、幂等和结果核实 |
| 业务记忆 | 有来源的陈述、确认程度、有效性、冲突和复用范围 |

跨模块操作由明确的应用服务组织。界面和 Agent 节点经业务操作入口协作，不能自行跳过权限和状态门禁。Agent 可提交分析结果或动作建议；审批决定来自具备当前权限的人。材料知识发布、方案批准和外部动作批准须遵守各自对象的业务规则，不能仅因使用相同的授权组件而混用批准结果。

例如批准方案时，应用服务组织身份、提交快照、证据和风险检查，保存批准及待执行动作；外部执行由发布模块处理。具体事务、调用契约和一致性策略尚待设计。

比较过的另一方案是主要沿用 `agents/tools/schema` 等技术类型组织全部新增功能。选择按业务职责组织，目的是明确状态维护、授权和外部写入的归属。目录映射和具体类名尚未确定；这不是立即搬迁现有代码的授权。

### 3.7 TD-007：关系记录、JSONB 内容修订与追加审计分工

状态：设计方向已确认。确认日期：2026-11-02。Round 4 Q7 用户回复“7) 同意”。

关系表保存稳定对象身份、业务状态、来源依赖、审批及逐项发布结果；JSONB 保存方案内容修订；追加审计记录保留操作者、时间、对象修订、动作和结果。正文以指定修订的 JSON 快照为准，权限和业务状态以对应关系记录为准。派生查询索引不提供另一套独立编辑入口。

每次保存形成新的内容修订并保留旧修订；提交和批准绑定具体修订。发布结果追加记录，导出将指定正文与相应审计封套组装，不能因更新发布进度改写已批准正文。表结构、约束、摘要计算、写入事务和版本校验仍待细化。

比较过的另一方案是把正文全部拆为关系表、导出时组装 JSON。选择混合存储以保留完整的内容修订，同时显式管理身份、权限和业务生命周期。代价是必须规定每个字段的唯一权威来源，并校验引用、内容修订和索引的一致性。

详见[领域数据与权限设计](领域数据与权限设计.md)。该专题当前仅展开已确认的存储方向、需求约束和待决问题，不是已批准的数据模型或机器 Schema。

### 3.8 TD-008：统一后端授权与显式来源依赖

状态：设计方向已确认。确认日期：2026-11-02。Round 5 Q8 用户回复“8)同意”。

首版权限由统一后端授权组件校验，关系数据显式记录对象授权范围和方案修订实际依赖的来源。登录主体从已验证 JWT 取得；后端核查当前用户和角色、操作权限、业务状态、归属对象授权以及派生物完整来源依赖。调用入口包括业务 API、文件读取、检索、导出、checkpoint 恢复和 MCP。

数据库行级安全（RLS）作为额外防线尚未纳入首版必需机制。PostgreSQL schema 分组不等同数据隔离，行权限也不替代业务授权。由用户、角色和资源授权关系组成的具体数据模型、缓存失效方式和数据库账号权限仍待细化。来源无法解析或当前授权不足时拒绝读取和执行。

设计时采用的越权案例：销售无权读取某安全来源时，即使方案正文未显示该来源的显式引用，也须检查实际输入依赖并拒绝访问整个派生物。已批准要求见业务需求第2节/P02 和 AC04、AC05、AC23。

### 3.9 TD-009：业务写操作使用修订校验与短事务

状态：设计方向已确认。确认日期：2026-11-02。Round 5 Q9 用户回复“9)同意”。

保存、提交、批准及分析结果回写检查预期内容修订、目标状态及适用的尝试身份。业务状态、对应审计和修订的必要数据库写入采用短事务；校验条件不成立时拒绝过期操作，不自动覆盖新修订或旧请求绑定的快照。

持有用户编辑锁不作为默认并发机制。模型调用、用户等待及 MCP 网络请求不包在长期数据库事务中；其幂等、执行归属和恢复仍按工作流及发布专题设计。条件更新的具体数据库写法、事务范围及冲突响应仍待细化和测试。

过期操作示例：两个窗口均读取修订 3；第一窗口创建修订 4 后，第二窗口提交修订 3，服务端返回可恢复的冲突，要求刷新，不能悄悄覆盖或批准旧快照。该设计落实业务基线 P01/P06 和 AC11、AC13、AC26。

### 3.10 TD-010：首版预置账号一账号一角色

状态：设计方向已确认。确认日期：2026-11-02。Round 6 Q10 用户回复“10)同意”。

首版三个预置演示账号分别只绑定一个有效角色：销售、售前架构师或审核人。角色决定可执行的操作类型；角色本身不授予所有商机、任务或知识版本的访问权。首版不引入多角色叠加、临时角色切换或角色管理控制台；具体 JWT 主体字段和账号种子配置待细化。

该选择让禁止自审批和操作责任保持明确。未来如需多角色，应单独定义权限合并、审批责任和审计含义，不能在首版通过同时绑定多个角色绕过边界。

### 3.11 TD-011：按用户和资源范围授权，默认拒绝

状态：设计方向已确认。确认日期：2026-11-02。Round 6 Q11 用户回复“11)同意”。

首版为用户显式记录可访问的商机、任务和知识版本及允许的操作范围；没有匹配授权时默认拒绝。客户材料归属于商机或任务，内部知识按具体知识版本及其适用授权判断。访问方案或其他派生物时，除归属对象授权外，还要检查所有实际输入来源的授权闭包。

### 3.13 TD-013：JWT 标识身份，服务端读取当前授权

状态：设计方向已确认。确认日期：2026-11-02。Round 8 Q13 用户回复“13) 同意”。

### 3.28 TD-028：业务审批先持久化，再推进图恢复

状态：设计方向已确认。确认日期：2026-11-02。Round 16 Q29 用户回复“同意”。关联决策：[ADR-0005](../../adr/0005-idempotent-graph-resume-intents.md)。

与每次点击创建独立恢复请求、仅依赖节点去重相比，稳定意图及图内回执更便于在回执丢失后解释和对账，但需要协调业务执行权、图状态与业务结果。领取 fencing 按 TD-031 细化；消费回执写入时序及 checkpoint 缺失或不可判定时的受控处置仍待设计。本决策不是已实现协议。

### 3.30 TD-030：批准动作标识直接作为本地 MCP 幂等键

状态：设计方向已确认。确认日期：2026-11-02。Round 16 Q30 用户回复“同意”。关联决策：[ADR-0006](../../adr/0006-approved-action-id-as-idempotency-key.md)。

每个批准动作具有稳定动作标识和固定参数摘要，并直接将该动作标识作为本地 MCP 目标的幂等键。同一动作的有界重试和恢复沿用原键；每次技术调用另有独立调用标识及结果。目标端发现同键对应不同参数摘要时拒绝请求且不覆盖原记录。写入结果未知时先按原键核实，不换键重试；动作参数改变须重新审批并产生新动作标识。

相较另建稳定幂等键并维护动作到幂等键的一对一映射，直接复用动作身份减少一层映射和恢复歧义。可验证幂等能力及不具备能力时的门禁按 TD-032 处理，摘要覆盖范围按 TD-034；规范化算法、目标端键格式和重复请求响应、按键查询的一致性及适配层补足能力仍待设计，不表示现有 MCP 或目标已经实现该契约。

### 3.31 TD-031：恢复意图领取采用单调 fencing 代次

状态：设计方向已确认。确认日期：2026-11-02。Round 17 Q31 用户回复“同意”。关联决策：[ADR-0005](../../adr/0005-idempotent-graph-resume-intents.md)。

同一恢复意图每次重新领取执行权时递增 fencing 代次；推进图和写入处理回执均须携带当前代次。checkpoint 或业务状态已接受较新代次后，旧领取者的迟到推进及回执必须被拒绝，不能与新领取者并发完成恢复。

单靠领取租约过期不能阻止暂停后恢复运行的旧执行者。单调 fencing 代次显式隔离过期持有者，但其分配、传播、checkpoint 接受新代次及回执提交的原子边界仍待设计；若图存储不能拒绝旧代次，方案需保持待核实，不能声称 fencing 生效。本方向未实现或验证。

### 3.32 TD-032：MCP 写入必须通过可验证幂等能力门禁
