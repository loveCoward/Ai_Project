## 1. 目标、依赖与边界

【一级·基线】二B将合法、就绪的任务输入，经受限检索和四类专业分析，形成带来源、覆盖、风险、澄清项及一次受约束Reflection的Proposal Draft。Proposal Analysis Attempt、任务、版本、内容修订和graph thread保持独立。正确识别不支持或关键风险可以是分析成功，不能因无法批准就虚构覆盖。依据：需求第3—5、7—9节，架构总览二B分工。

【二级·现状】当前售前模块已有身份、授权、来源闭包、草稿修订及材料/知识/索引应用服务；尚无售前分析执行链。以下是本轮源码证据，未执行工程测试：

| 范围 | 可核验代码 | 复用边界 |
| --- | --- | --- |
| 授权和来源 | `src/presales/access/policy.py`的`source_closure()`；`application/service.py`的草稿读取与依赖登记 | 可复用统一门禁；尚无分析实际读取集合及Evidence Snapshot聚合 |
| 草稿和修订 | `domain/contracts.py`的`DraftContent`；`application/service.py`的`_save_revision()` | 只是阶段一草稿输入，`analysis_attempt_id`写为`None`，并非完整Schema 1.0；`_task()`要求任务为`new`，分析落稿不能原样套用 |
| 作业控制 | `materials/service.py`解析执行代次；`indexing/service.py`索引取消与提交检查 | 可参考旧执行拒绝和取消竞争处理；不是分析槽位、Attempt或恢复实现 |

## 2. 工程方案与取舍

【三级·建议】以下是作者工程默认方案，未逐项获批，也不是运行结论。

| 选择 | 推荐方案与理由 | 备选及代价 |
| --- | --- | --- |
| 后台寿命 | FastAPI生命周期内的执行监督器，独立于请求/SSE管理任务；数据库保存已接受命令及占位，提交后唤醒监督器 | 请求内`astream()`不能保证关页继续；独立队列服务增加部署和恢复成本，超出首版范围 |
| 启动交接 | 短事务建立Attempt、槽位、thread和命令回执；监督器领取后才运行；持久记录支持“提交后尚未唤醒”核对 | 仅`create_task()`会在提交与调度间丢失执行；不使用FastAPI请求结束后台回调作为唯一保障 |
| 图结构 | 显式StateGraph和确定的依赖边，Router仅选择允许的分析计划/参数 | 自由Supervisor循环难以约束预算、完整性和一次Reflection |
| 并发权威 | PostgreSQL任务占位与单例全局槽位，事务锁和执行代次共同约束 | 进程锁不能处理跨进程启动和迟到执行 |
| 重启恢复 | 核实后由架构师显式继续原Attempt，保留预算、历史和thread | 直接自动续跑会越过重新鉴权；一律结束旧Attempt较简单，但丢失可恢复进度；用户本轮选择前者的受控形式 |
| SSE | 经Bearer认证的fetch流，推送持久运行投影的修订与失效通知；快照是事实来源 | 不补播全部token；直接开放AG-UI会暴露过宽状态，原生EventSource不能直接附Bearer头 |
| MCP | 复用二A的后端受控stdio接入，二B增加只读`read_context`适配 | 不引入真实CRM、独立ACL或写工具；本地子进程兼容与回收仍待验证 |

【三级·建议】首版运行一个售前分析监督器，不承诺高可用或生产并发。多个API实例/重复监督器仍必须被数据库占位拒绝，不能把“通常只启动一个进程”当排他保证。数据库中只登记已经成功取得槽位的执行，不接受忙时待排队任务；监督器核对未派发记录是交接补偿，不是排队服务。

## 3. 认证与外发前置契约

【一级·基线】启动、取消和重跑由售前架构师发起；查看仍受对象和全部实际来源限制。后台上下文绑定已验证发起人、任务、输入修订及启动允许范围；范围取启动上限与当前授权交集，新增授权不扩展旧Attempt。浏览器JWT自然过期或关页不取消合法后台分析；停用、撤权或Attempt失效后停止后续受限操作，返回结果不能写入当前候选。依据：P02、TD-015至TD-017、双入口设计。

【三级·建议】每个节点开始、读取/检索、调用模型或MCP前，以及结果接收、持久化和落稿前，检查当前执行代次、任务/Attempt状态、取消标记、当前授权、来源就绪及外发配置。计算后再验权不能撤回已经发出的请求，因此同时记录调用发起与返回身份，撤权后的迟到结果隔离保存或仅保存受限元数据，不继续送往下游。

【一级·基线】模型、Embedding、Reranker、Judge、观测和工具的接收方只能来自显式配置。读取权限不等于外发授权；Prompt、客户文本和工具结果不能改端点、actor、grant或批准状态。工程测试无Key运行，Fake必须显式选择；真实调用失败不得静默切Fake。依据：需求第2.3、7、9节与P02/P09。

【三级·建议】Attempt记录实际模式、模型/配置/模板版本、允许数据类别和接收端别名；实际端点身份保存在受限provenance，输出移除凭据及URL秘密参数。节点凭服务端Attempt上下文重建权限，不保留浏览器JWT。stdio调用凭证短期有效且限定audience，由传输上下文携带，不能进入工具业务参数、Prompt、checkpoint或日志；子进程只继承必要环境。运行页和SSE不返回服务凭据或完整graph state。

## 4. 数据和来源契约

【三级·建议】复用阶段一资源、版本、直接依赖、命令回执和审计；下表是逻辑记录建议，不冻结物理表名、机器Schema或SQL实现。

| 记录 | 必要信息 | 一致性要求 |
| --- | --- | --- |
| Analysis Attempt | task/actor、锁定输入清单及修订、启动范围上限、模型模式/配置、thread、执行阶段/结局、运行修订、执行代次、预算、取消及恢复原因 | thread服务端生成且一Attempt一绑定；开始与任务/全局占位同事务；不得换actor续跑 |
| 执行占位 | 任务占位、全局槽位、Attempt、执行代次、owner、存活时间、在途调用 | 同任务至多一个有效Attempt，全局至多一个执行者；租约到期只触发核实 |
| 节点执行/调用 | 节点、调用ID、参数摘要、来源依赖、开始/截止/结束、尝试次数、结果和错误/降级 | 重试继承同节点预算，技术调用ID不同；来源/身份可信字段由服务端写入 |
| 节点产物 | 不可变内容修订、所属Attempt/代次、直接输入、就绪、校验结果 | 来源关系持久且闭包完整后可见；旧代次不可更新当前投影 |
| Evidence Snapshot | 实际使用的来源版本/定位、内容校验值、适用性和检索配置；直接依赖另行权威登记 | 不只保存最终引用；MCP背景、原材料、专家输入和Reflection新增来源都计入依赖 |
| 运行投影 | task/Attempt、单调`run_revision`、节点摘要、错误/降级、终态、结果就绪、结果修订身份 | 与相应业务变化同短事务递增；供快照/SSE使用，不以事件到达顺序覆盖业务事实 |
| 恢复记录 | 稳定请求身份、Attempt、固定输入/中断目标、预期修订、核实结论、领取代次、结果回执 | 重复同意图复用身份；同键异参拒绝；未确认消费与未执行不能混为一谈 |
| 背景输入声明 | Opportunity、必需/可选/未确认、声明人和修订、读取状态及来源快照 | 随Attempt锁定；不能因读取失败改成可选；成功空历史与失败分别表示 |

【一级·基线】任务/版本业务状态沿用P01，不把`running`、`waiting_human`、`reconciling`等执行阶段塞进任务或版本枚举。任务“已取消”不可复活，重新开展同类工作须新建任务。授权失效Attempt即使后来恢复授权，也须新建Attempt。依据：需求第4.2节、TD-017/TD-027。

【三级·建议】Attempt内部执行阶段可为`accepted`、`running`、`waiting_human`、`reconciling`、`finished`；结局另记成功、失败、材料待补充、取消、授权失效。`waiting_human`仅用于已持久的人工中断，不能以它包装未知调用；`reconciling`不是成功或已安全释放。终态结局不可改写，后续核实追加记录并推进可用性投影，不把失败改为成功。精确编码由后续契约生成，不另建前端独立枚举。

【三级·建议】来源范围上限区分任务材料的固定版本清单与可检索知识/背景的允许资源范围。任务材料版本、输入必需性和产品/部署约束在启动时锁定；在已锁定允许范围内检索时仍选当前适用且已发布版本，并把实际版本写入Evidence Snapshot。续跑复核已使用证据的有效性；停用、适用范围变化或无法维持原依据时，不偷偷替换历史快照，结束或报告需要新Attempt。历史快照不保证真实模型逐字复现。

## 5. Attempt、槽位、取消与恢复协议

### 5.1 启动及后台寿命

【一级·基线】同任务/全局活跃分析上限为1/1，全局忙时拒绝而不排队；运行期间输入快照不得并行编辑。生成调用120秒，MCP单次10秒，主动运行总预算10分钟，可重试技术错误初次后最多2次；人工等待不计主动预算，Reflection自动修订最多一次。所有值配置化并记录实际值，均非实测SLA。依据：P01/P08、TD-025/TD-026。

【三级·建议】启动协议：

1. 先检查角色、来源声明、输入清单就绪、背景必需性已确认、显式模型模式/配置、上下文容量及任务可启动状态；不得默认把未分类失败材料或未确认背景当可选。
2. 短事务按固定锁序锁全局槽位和任务，重验预期任务/输入修订、当前授权及状态；确认没有原Attempt、在途待核实执行或冲突发布，原子写入Attempt、独立thread、两级占位、`analyzing`任务状态、运行投影、命令回执和审计。
3. 事务提交后返回已接受身份并唤醒监督器。监督器以数据库条件领取执行代次；即使响应丢失，客户端也按原请求身份查询，不能换键再启动。监督器未领取时不得向外发起调用。
4. 监督器驱动LangGraph并监督子任务，在节点边界和调用截止时间检查预算。示例默认心跳5秒、30秒未更新触发核实；两者是待验证技术参数，过期绝不直接抢占。

【三级·建议】请求返回、SSE断线、退出登录仅结束交互/订阅，不取消监督器任务。服务优雅关闭时停止领取和新调度，保存检查点与调用登记，在有限关闭期限内等待或中断本地调用；无法确认的保留`reconciling`。异常退出后的首次启动只扫描/核对，不自动恢复模型调用。运行期数据库不可用时停止新外发，不能继续仅凭内存授权执行。

### 5.2 结果提交与终态

【三级·建议】节点完成先保存不可变产物及来源关系，跨checkpoint/文件内容以待就绪记录衔接，复用TD-021/TD-024。分析完成使用专门应用命令落稿，不绕过现有`new`限制直接调用手工草稿保存入口，也不向运行账号开放任意状态更新权；所需数据库最小权限须显式迁移。

【三级·建议】节点使用稳定执行身份，绑定Attempt、节点、输入修订及前版/Reflection修订阶段；技术重试另记调用身份。恢复重入节点时先核对已提交产物与该执行身份，存在且仍合法则复用，不能再次调用模型覆盖结果；业务产物已提交而checkpoint落后时按同一身份对账。缺少产物不能单独证明调用未执行，仍须核对调用登记和在途结局。唯一约束与条件写入防止同一节点身份产生两份权威结果。

【三级·建议】最终短事务同时重验actor当前权限、全部实际输入来源、当前Attempt/代次、输入修订、候选版本预期修订、未取消、四类产出/Schema/Reflection检查结果；然后保存新草稿修订、来源、Evidence Snapshot身份和当前候选指针，任务转“已分析待提交”，Attempt成功、投影递增、回执和审计一起提交。checkpoint完成不是落稿成功。成功后checkpoint补写失败可追加恢复记录，但不能生成第二份候选或回退业务成功。

【三级·建议】结构完整且诚实标注“不支持/关键风险/待澄清”的结果可以结束分析并成为草稿，业务门禁仍显示阻断；“已分析待提交”表示分析完成，不保证可立即提交或批准。关键Agent/模型失败、结构缺损或Reflection未完成保留部分产物并转任务失败；关键材料不足转待补充，不能把部分输出当完整草稿落为当前分析结果。之前有效草稿保留，不由失败尝试覆盖。

### 5.3 取消与在途调用

【一级·基线】取消停止新调度及未发起副作用，保留结果并标记取消，不生成新正式方案；已在途动作须核实。任务尚未正式批准时架构师可取消，已取消任务后续工作新建任务。依据：P01/P02/P04、AC19。本方案不新增“只停本次分析但复活已取消任务”的业务操作。

【三级·建议】取消命令锁定同一任务/Attempt行，持久取消标记、失效执行代次、任务已取消、审计和运行修订；监督器收到通知后停止新节点，尽力取消本地调用。客户端中断HTTP不能替代此事务。重复取消用原请求身份核实；已取消返回同一结果，不重复改变终态。

【三级·建议】取消与落稿的胜负由业务事务串行确定：取消先提交则旧执行无法落稿；落稿先提交后仍允许按P01取消未批准任务，但保留已形成草稿并标明任务取消。对已批准任务拒绝此取消命令。取消后的迟到返回不能发布进度正文、写当前候选或激活旧checkpoint。

【三级·建议】取消的业务终态与执行排空分开显示：界面可显示“已取消，正在核实在途调用”。全局槽位不因取消回执立即释放；先确认本地执行停止、子进程退出或已失效，旧代次在checkpoint/业务写入边界被拒绝，在途调用有确定结局或达到可核实的截止边界。无法确认则保持受限占位、拒绝新分析，不能以租约到期、HTTP已断开或“读工具无写入”为由宣称安全结束。已发送模型请求可能继续计费，取消不承诺供应商撤回；二B没有外部业务写入权限。

### 5.4 重启核实与受控续跑

【一级·基线】2026-11-10用户同意：允许核实后受控续跑原Attempt；重启不自动调用模型，重新登录后由架构师显式继续；保留原预算与Reflection次数，无法安全确认保持待核实，确认不可恢复后结束旧Attempt，重跑创建新Attempt。该确认细化TD-024至TD-026，不扩展撤权/取消后恢复权限。

【三级·建议】核实与恢复按以下顺序处理：

1. 启动扫描旧owner、心跳、两级占位、在途调用登记、业务回执、结果就绪记录和checkpoint，标记需核实。仅心跳超时不能证明旧进程或调用停止。
2. 先证明旧执行已停止或被可靠隔离；检查业务是否已经落稿。业务已成功且checkpoint滞后时只修复回执/就绪投影，不重新生成；旧调用已返回但未落库时，校验来源及摘要后受控补记，不假定可复用。
3. 对模型调用结果未知，不直接再次调用；记录未知、原截止与已消耗次数。确定调用无法继续接收且旧写入已被fence后，可结束该调用并按剩余预算决定是否允许有界技术重试；无法确定继续待核实。MCP只读调用也保留失败/未知身份，重读只在安全隔离且预算允许后发起，不能伪称复用了原背景快照。
4. 架构师重新鉴权，以原Attempt和稳定恢复请求发命令；服务重验原发起人、当前授权、输入/候选修订、来源有效性、任务及Attempt有效、剩余预算、可解释的checkpoint边界。换人不能接管原发起人上下文，需依基线另建Attempt。
5. 短事务重新取得全局槽位、保留任务占位，递增执行代次并记录固定恢复意图；全局忙则拒绝本次继续、保持可恢复，不排队。领取后监督器从确认边界继续；重复恢复核对业务与图内回执，不盲目重复推进。
6. checkpoint缺失/损坏、输入发生变化、已用来源不再有效、主动预算耗尽或无法保证旧代次拒写时，不续跑。保留原因；能明确判定不可恢复且完成在途核实后结束旧Attempt并释放占位，允许在合法任务状态下另建Attempt；尚不能判定则继续待核实。

【三级·建议】主动预算累计各次实际运行区间的墙钟时长，并行节点不重复累计；不包含已核实无执行的服务停机和已持久人工等待，尚在途调用不能仅因主进程退出就排除。每个调用还受自身截止和节点重试上限约束。进入调用前持久记录预算、截止及已用重试次数；崩溃区间无法精确核实时按登记上界保守计入预算，不重置总10分钟或技术重试计数。纯计算/结构校验也受主动预算截止约束。

【一级·基线】TD-033要求在checkpoint持久化提交边界条件校验当前fencing代次，处理回执同样受限；调用前读取代次不够。saver不能拒绝旧代次时恢复保持待核实。

【三级·建议】后续实现须验证受控saver适配，在每个checkpoint及pending writes提交事务内锁定/比较Attempt当前代次和允许写入状态，业务回执使用同样的条件写入。取消和接管与该校验串行化，不能仅在外层包装一次读取后调用独立连接的原saver。若锁定依赖的saver无法提供该事务边界，应阻断受控续跑而非降低门禁；具体适配源码和跨schema最小权限列为实现前技术门禁。

### 5.5 人工等待与阶段三交接

【一级·基线】人工interrupt须保留Attempt/checkpoint和任务输入锁、释放全局执行槽位；恢复重新占位和鉴权，等待不计主动预算。审批先落业务记录再按稳定意图推进图，旧fencing不得写入。依据：TD-027至TD-029、TD-031/TD-033。

【三级·建议】二B正常路径在草稿落库后结束分析计算，不提前实现审批interrupt或审批恢复入口。关键材料/澄清不足形成待补充或带明确阻断的草稿；修改输入后重跑创建新Attempt。阶段三再将固定草稿交接审阅/审批子流程，复用执行基础并实现上述人工等待协议，不能把关页、缺证据或失败一律伪装成人工中断。

【三级·建议】为阶段三保留的顺序约束是：先持久checkpoint及有身份的中断目标，再由业务短事务核对其就绪并记录人工等待、释放全局槽位；崩溃在释放前仅导致保守占用，不能提前释放让旧执行继续。恢复固定原中断目标、重新占位和递增代次后才推进；本阶段只验证执行基础的隔离契约，不声称完整审批/人工等待链路通过。

## 6. 分析DAG、Schema 1.0与Reflection

### 6.1 数据依赖与四类产出

【一级·基线】需求、架构、产品案例证据、技术安全交付风险四类专业分析均为关键产出，不能用辅助能力降级掩盖缺失；Reflection检查覆盖、引用、风险和澄清遗漏，最多自动修订一次。依据：需求第7、9节及P03。

【三级·建议】显式依赖顺序如下，节点名为逻辑名：

```text
启动门禁 → 固定输入/背景读取 → 意图识别与Router计划
    → 需求分析（保留全部原始出处和稳定需求身份）
    → 产品/案例证据分析（依赖需求，调用受限检索和只读目录）
    → 架构分析（依赖需求与证据，输出部署/集成及条件）
    → 技术/安全/交付风险分析（依赖需求、证据与架构）
    → 汇总与确定性校验 → Reflection检查 → 至多一次修订
    → 修订后校验/硬门禁比较 → 受限草稿落库
```

【三级·建议】首版先采用容易核查的依赖顺序，不为展示多Agent而强行全并行。各专家内部的独立只读查询可有界并发，必须属于同一Attempt并共用预算；Router只能生成白名单节点计划，不能新增工具、放宽权限、删去关键专家或开启循环。模型不能自主创造“审批已通过”或写工具调用。

【三级·建议】需求身份由服务端维护，拆分/合并保留原始出处和对应需求基线；模型建议合并未经确认不改变覆盖分母。每个专家输出结构化结果、事实/建议/待确认属性、证据ID、限制和已执行检查。汇总不能用自然语言掩盖专家缺失；没有风险/问题时允许空列表，但须记录已执行对应检查。上下文不够覆盖关键输入时明确失败/待分拆，不静默截断后标记完整。

### 6.2 Schema 1.0与校验层次

【一级·基线】P06规定JSON为唯一内容源，schema_version从`1.0`开始，含以下业务区块。冻结正文与追加审计封套分层；实际审批和发布能力不因字段存在而提前完成。

【三级·建议】二B产出Schema契约及校验器的范围如下；本文只定义逻辑结构，不创建机器JSON Schema，也不把当前`DraftContent.schema_version="1.0"`当成完整实现。

| 区块 | 二B应形成的信息 | 禁止伪造/后续职责 |
| --- | --- | --- |
| identity | customer/opportunity/task/Attempt/version/content revision、schema_version | 身份由服务端写；不信任模型自报 |
| provenance | 输入版本、配置/模板/模型/端点身份、模式和时间 | 不含秘密；未知模型修订如实标记 |
| access | 归属、权威来源依赖身份和受限访问说明 | 投影不能替代服务端实时授权，也不暴露全量ACL |
| requirements | 原始出处、必须性、当前范围、五类覆盖、证据/风险/澄清关联 | 重要性与覆盖状态不混用，不删不支持项 |
| coverage | 固定需求基线、分母/完全覆盖分子/各状态数、比率 | 程序计算，不让模型提供权威百分比 |
| evidence | 来源/版本/位置/片段身份、适用范围、类型、授权关联 | ID和位置须解析，不能由模型编造页码 |
| solution | 建议方案、部署/集成、假设/限制和交付注意 | 报价/日期/合同建议明确非绑定或待确认 |
| risks | 六类风险、等级、依据/影响/缓解/责任人及处置状态 | 未有真实处置记录则待处理，不生成接受决定 |
| clarifications | 问题、关键性、关联、已有来源回答及状态 | 无客户确认来源不能标已解决；交互治理留三 |
| review / approval | 显式尚未提交/尚无决定，保留契约位置 | 不生成虚假审核人、批准身份或允许动作集；三实现 |
| execution | 节点结局、失败/降级、预算、Reflection前后身份及检查 | 发布未执行明确表示，不能伪造逐项成功；四实现 |
| memory_updates | 带来源/范围及可信、有效状态的拟复用陈述 | 仅候选；写入未执行，治理与确认留三 |

【三级·建议】兼容现有手工草稿：在后续迁移/读取适配中显式区分阶段一存储形态与完整方案形态；按已知格式和完成状态返回，旧草稿不能仅凭同为`1.0`通过完整方案校验。不得静默补空必需产出假装完整。机器契约、OpenAPI和前端DTO以同一后端定义生成，具体生成工具及兼容迁移在实现计划中锁定。

【三级·建议】校验分为四层：结构类型与必需区块；ID/版本/引用定位和跨区块关系；确定性业务门禁；语义支持与质量评估。前三层工程测试能验证实现，最后一层需要真实模型和人工/冻结数据评测，Schema合格不能证明“引用真正支持论断”。

【一级·基线】AC07—AC10落实为：五类覆盖状态保留，范围外仍入分母；10条中6条全覆盖即60%，范围空显示不适用并阻断提交；必须需求未覆盖/待澄清/范围外阻断批准，部分覆盖需审核人明确接受；严重风险不可豁免，高风险需明确接受，中风险需处置。冲突不静默裁决，无来源澄清不改变关键结论。依据：需求第5节/P03。

【三级·建议】二B返回确定性门禁清单和证据，不执行正式提交/批准。接受状态只引用真实已有决定，二B不能自行造记录解除阻断；阶段三必须在提交/批准时重新执行门禁，不能把二B结果当永久通行证。

### 6.3 一次Reflection与前后保留

【三级·建议】先保存汇总前版的不可变产物与实际来源，Reflection输出问题、证据及建议修改，再由一次修订步骤形成后版。未发现修改项时仍保留“检查完成、无修改”的后版关联和检查记录；若没有有效检查，不允许用复制前版冒充自检完成。前后产物分别保留内容身份/摘要、来源依赖、同一需求基线、节点/调用身份和变更清单，运行页可比较。

【一级·基线】自动修订最多一次；模型调用技术重试不能扩大修订次数。Reflection检查须完成或由有权限人员补充复核；人工补救不算自动Reflection能力通过。AC21要求保留两版并可检查质量差异，AC27要求无有效配对计失败而非删除样例。依据：P03/P07/P08。

【三级·建议】修订次数在创建修订执行身份时持久占用，恢复复用同一身份；同节点技术重试只处理未完成/确认失败的调用，不创建第二个业务修订步骤。结果未知先核实。后版对结构、完整性、引用/权限、必须需求、风险及未确认承诺重新检查；不得删需求缩分母、无依据降风险、隐藏缺证据或伪造风险接受来通过。

【三级·建议】确定性检查发现后版新增违规或硬门禁退化时，保留两版和失败原因，隔离后版，前版只作为部分成果保留，不宣称Reflection完成或自动选“看起来更好”的一版落稿。Reflection调用耗尽、缺前后版或无法完成必要检查时，任务失败并标待人工处理；阶段三可提供有身份的人工复核补救，二B不提前开放该写入口。语义质量改善不能仅由结构差异推断，后续能力评测单独判定。

## 7. 接口、只读MCP、快照/SSE与运行页

### 7.1 应用和REST契约

【三级·建议】下列为拟议应用契约及HTTP映射，不是已有路由；最终路径/DTO随实现统一生成。

| 命令/查询 | 建议HTTP | 关键约束 |
| --- | --- | --- |
| `start_analysis` | `POST /api/tasks/{task_id}/analysis-attempts` | 稳定request ID、expected task/input revision、显式模式、背景必需性；不接受actor、grant、thread或端点 |
| `get_command_result` | `GET /api/commands/{request_id}` | 仅当前主体可核实的命令；受限结果再次验权；已知受理回执丢失不换键重试 |
| `get_run_snapshot` | `GET /api/tasks/{task_id}/analysis-snapshot` | 当前Attempt/历史身份、运行修订、节点、终态/排空、就绪和结果引用；按当前来源闭包授权 |
| `get_attempt` / `read_analysis_artifact` | `GET /api/analysis-attempts/{attempt_id}`及其受限产物 | 明确历史Attempt；失败/取消产物显著标记，不能冒充当前候选 |
| `cancel_task` | `POST /api/tasks/{task_id}/cancel` | 架构师、预期修订、当前Attempt及request ID；取消任务含义不变 |
| `continue_analysis` | `POST /api/analysis-attempts/{attempt_id}/continue` | 重新鉴权、稳定恢复身份、预期修订及核实边界；全局忙拒绝，不自动排队 |
| `subscribe_run` | `GET /api/analysis-attempts/{attempt_id}/events` | fetch Bearer；任务/Attempt身份不可跨订阅混用；仅受限进度投影 |

【三级·建议】启动成功仅返回已接受（可用202）及查询身份；受理不表示模型已成功运行。修订冲突、同任务重复、全局忙、配置缺失、材料/背景未就绪、资源超限和恢复待核实使用稳定错误码，前端给出对应动作。未知对象与无权对象统一不泄漏响应；命令回执查不到不能证明命令从未提交，重发仍沿用同一request ID和参数。

### 7.2 快照与事件竞争、终态

【一级·基线】SSE只传受限进度，不承担业务命令、完整审计或审批恢复。断线后重新鉴权、取当前业务快照；不承诺重播全部临时token。必须消除“读取快照后尚未订阅期间已结束却永久显示运行”的缺口。依据：双入口设计第3—5节。

【三级·建议】采用“建立订阅并缓冲 → 读取快照 → 按修订核对 → 持续重查”的协议，服务端不依赖易失内存通知作为唯一事件源：

1. 订阅鉴权并绑定task/Attempt，发送`ready`及当前`run_revision`。服务端从已提交数据库投影检查修订变化；进程内通知只用于加速，丢通知不影响最终可见。
2. 前端收到`ready`后缓冲通知并GET快照。快照在同一短一致性读取中取得任务/Attempt、修订、终态、就绪和产物身份，不能混合不同提交的字段。
3. 应用快照修订R，丢弃同一Attempt中修订不大于R的通知；收到更高修订就重新取快照，不按可能丢失/乱序的节点补丁拼出事实。不同Attempt的修订不可比较，切换必须读取任务当前指针并清理旧缓冲。
4. SSE建立后总是检查一次当前投影；如果已经终态，立即通知并要求查询，不能等一个不会再出现的新事件。终态业务事务先提交再通知；终态事件只是提示，结果是否就绪仍以快照为准。
5. SSE发送`changed`、`terminal`和不含正文的心跳。建议每2秒检查投影、10秒心跳；前端非终态时另以15秒刷新快照作为兜底，重连、窗口重新激活和终态提示均立即重查。参数是待验证起点，不是延迟承诺。
6. 连接EOF、代理超时、网络错误或仅收到`[DONE]`不构成业务成功。重新连接从`ready`和快照开始；事件ID只用于修订去重，不承诺按`Last-Event-ID`完整回放。缓冲溢出时丢弃缓存并重新同步，不截断为完整运行历史。

【三级·建议】`run_revision`在锁定同一运行投影行的业务事务内递增；不能用独立sequence分配顺序冒充提交顺序。一个事务内的节点/终态变化与投影一起可见。SSE不发Prompt、工具参数、模型推理链、原始token、未过滤证据或完整错误栈；节点正文通过独立受限产物读取取得。

【三级·建议】建立订阅及每次发送前复核token有效期、账号、对象、Attempt实际来源闭包与当前权限；心跳也触发周期复核。token到期停止订阅，前端清受限缓存并重新登录；撤权拒绝后续推送/读取并清缓存。合法后台不因token自然到期停止，但后台发起人撤权按TD-017终止；读者撤权与发起人撤权分别处理。网络中断时显示未同步，不能把缓存旧状态显示成当前已核实结果。

### 7.3 Opportunity Workspace只读背景MCP

【一级·基线】只读商机背景接入属于二B，Product Catalog只读目录复用二A；外部创建和发布写工具留阶段四。首版只接确定性本地Mock，不接真实CRM。用户本轮确认背景必需性在启动前明确并锁定：必需读取失败停止完整分析，可选失败带缺失说明继续，未确认不按可选处理，成功空历史正常。

【三级·建议】`read_context`仅接受允许的Opportunity身份及有界读取参数。后端注入可信主体/Attempt与调用凭证，MCP共享授权组件重建当前范围，任务权限不能向上推导整个商机访问权。只有任务授权但没有商机背景权限时，不能尝试读取再让模型过滤；背景必需则启动被拒绝，可选则记录不可用并在合法任务输入范围内分析。

【三级·建议】工具返回背景/历史记录的稳定ID、版本、来源声明、时间、可信/有效状态和读取结局。本地Mock背景通过共享资源/来源登记形成Evidence Snapshot可解析来源，不允许把未登记字符串作为可信事实送入图。工具没有来源版本或权限闭包不完整时返回契约失败，不能伪造evidence ID。商机专有信息不自动升为客户通用记忆，待确认/过期/冲突记录不可作确定事实。

【三级·建议】背景结果区分成功有内容、成功空历史、无权/不存在、超时、调用失败和契约失败；普通用户响应保持不泄漏边界，受限审计记录精确原因。必需失败停止完整分析并保留部分结果，按材料/输入缺失归待补充、技术不可继续归失败；可选技术失败可见降级继续，仍须满足四类关键产出及证据门禁。范围变更或改必需性须新的输入修订/Attempt，不能在原运行中翻标记绕过失败。

【三级·建议】`read_context`遵守10秒调用上限、初次后最多2次技术重试及总预算。工具发现/注册白名单只有只读能力；即使Mock包含后续写实现，二B客户端也不注册，服务端同样拒绝未经批准的写入。MCP输出中的提示、URL或“已批准”文本都是数据，不能更改计划、权限或调用目的端。
