## 1. 目标与成功标准

交付一个离线可测、权限明确、可迁移的领域数据基础，使后续阶段可以在不重构数据权威和授权边界的前提下增加分析工作流、审阅审批、发布恢复和工作台。

本阶段结束时，代码应能用显式迁移建立空数据库；持久化用户主体、角色、资源授权、Opportunity、Presales Task、Proposal Version/修订、材料来源和追加审计；从服务端身份读取当前授权并拒绝越权；按直接来源关系计算派生物访问范围；以短事务和预期修订拒绝过期写入；为本地文件保留数据库权威元数据及待就绪恢复记录。

阶段完成代表该阶段的离线工程契约已实现并有测试证据，不代表完整产品验收、Compose 交付验收、真实模型能力评测或整体技术设计获批。

## 3. 推荐方案与备选

### 3.1 数据访问与迁移

| 方案 | 维护成本与风险 | 结论 |
| --- | --- | --- |
| SQLAlchemy 2.x async + Alembic；复杂条件更新保留显式 SQL | 有标准模型、外键和迁移版本；需学习 ORM/迁移、在 `pyproject.toml` 显式声明依赖并验证 schema 分区 | **建议采用**。项目已有 PostgreSQL/psycopg 3 路径，阶段将增加的对象和外键较多，统一迁移有助于协作和升级审查 |
| 直接使用 psycopg 3 + 手写 SQL/自建迁移脚本 | 依赖变化较少，贴近现有 `src/memory/postgres.py`；需自行建立迁移版本、回滚/失败状态、模型映射和一致约束规范 | 可行但不作为默认；若用户更重视最小依赖，可在评审时切换，开发工作会转向维护自有迁移框架 |

推荐组合不等于已装入项目。业务层用 `AsyncSession`/SQLAlchemy Core 持有显式短事务；锁、条件更新、幂等登记和权限敏感查询可使用明确 SQL。LangGraph saver 继续使用它自己的 psycopg pool，不共享 ORM Session，也不把网络调用放进业务事务。

### 3.2 PostgreSQL 主版本

作者建议优先复用 Windows 已有 PostgreSQL 18 安装，验证通过后把后续 Linux Compose 目标统一为 PG18，减少额外安装和调试成本。当前 `compose.yaml` 的 PG16 只是继承配置，尚无售前数据库迁移；本机 PG18/PGVector 也只有安装文件存在性证据，不能写成服务已可用。采用 PG18 不代表本次修改 Compose 或迁移任何现有数据库。

实现时先核对锁定 psycopg/saver 对 PG18 的兼容性及测试数据库连通性。若存在可复现兼容阻断，则使用 PG16 作为两端共同基准并记录原因；这属于工程回退，不新增业务决策题。数据库权限测试只能针对选定主版本给出结论。阶段一不要求 pgvector 已安装，扩展和发行镜像在阶段二知识方案中锁定，Linux VM 运行验证留给阶段五；不得为完成本阶段擅自安装服务、访问已有业务库或连接 VM。

### 3.3 Schema 与连接角色

建议首批业务 schema：

| Schema | 首阶段职责 | 后续扩展 |
| --- | --- | --- |
| `iam` | 用户主体、角色映射、资源授权；账号密码和密钥不入库 | 授权维护历史和本机操作员绑定 |
| `presales` | Opportunity、Presales Task、材料/来源元数据、Proposal Version、内容修订和直接依赖 | Analysis Attempt、Evidence Snapshot、知识来源等按后续阶段迁移加入 |
| `audit` | 追加式业务操作审计，不存秘密和不必要的客户正文 | Review/Approval、授权变更、发布逐项结果的审计关联 |
| `workflow` | 首阶段不创建售前 checkpoint 表 | 后续核实 saver 的 schema/事务行为后再配置，不把 saver `setup()` 当业务迁移 |

schema 名是本方案的建议默认值，接受阶段方案时一并确认。数据库角色建议按职责分离：迁移角色拥有 DDL；业务运行角色可读 IAM、写允许的业务对象并追加审计，但不能修改角色/授权；授权维护角色只写授权关系和相应审计；LangGraph checkpoint pool 保持独立。角色 GRANT 必须通过 PostgreSQL 集成测试验证，schema 名本身不提供行级授权。

### 3.4 连接、事务与迁移入口

- 新增业务 `AsyncEngine`/pool，使用 psycopg 3 async 驱动；只从配置读取连接参数，口令使用 `SecretStr`，禁止打印连接串。配置模块独立于会初始化模型的 `src/core/settings.py`；导入数据层、运行迁移及授权测试不要求 LLM Key，也不自动读取仓库 `.env`。
- `src/memory/postgres.py` 的 saver/store pool 不与业务 pool 混用。当前 saver 配置为 autocommit；业务写事务需要显式 `begin` 并在短事务中提交。
- 迁移由显式 CLI/job 使用迁移角色执行；服务启动不对业务 schema 运行 `metadata.create_all` 或自动升级。
- 一个 Alembic 环境管理上述 schema，迁移 revision 有序并显式声明 schema。每次迁移只完成一项可审查改变；向前修复优先，降级只在可丢弃测试库演练。
- 阶段任务首先检查 LangGraph PostgreSQL saver 的版本与 `setup()` DDL 行为。若启动时需要建 checkpoint 表，必须将该初始化与业务 schema 迁移分离，明确所需数据库身份；不得让普通业务应用 role 获得任意 DDL 权限。
- 模型调用、文件读写、MCP/HTTP、人工等待都在数据库事务之外。业务状态、修订关系、来源依赖和审计中需要原子一致的部分在单个短事务提交。

### 3.5 领域记录分组

先按业务职责建关系，不把所有状态塞入一个可变 JSON：

| 记录族 | 阶段一至少要表达的内容 |
| --- | --- |
| `iam` | 稳定主体 ID、活动状态、一个有效角色、资源范围授权；账号密码和密钥不入库 |
| Opportunity | 稳定 ID、名称/场景元数据、创建主体、当前状态和创建/更新时间 |
| Presales Task | Opportunity 归属、目标、状态、发起主体、当前候选版本、输入集修订 |
| Customer Material/Source | 逻辑存储键、版本、校验和、来源声明、归属/授权范围、就绪状态；物理路径不作身份 |
| Proposal Version/Revision | 版本身份与生命周期在关系记录；每次正文形成不可变修订，结构化正文保存 JSONB 并绑定内容契约版本 |
| Direct Source Dependency | 下游修订/产物到直接上游身份及版本的边；禁止缺源、未授权引用和循环依赖；允许在当前授权下复用共享知识，完整来源闭包由关系遍历得出 |
| Audit Event | actor、动作、目标、目标修订、时间、结果、关联请求 ID 和非敏感摘要；追加写，不含凭据或客户原文 |
| File Readiness | 数据库中的待就绪/已验证状态、逻辑键、版本和摘要决定业务可见性；实际文件存在本身不开放读取 |

下表规定足以编制实现计划的逻辑主键及约束。物理列名、索引命名、类名和错误类命名由实现者按这些约束细化；机器契约在实现阶段生成，不再逐字段请求用户确认。所有 ID 建议使用服务端 UUID，时间使用带时区 UTC，修订为单调整数，业务状态沿用 P01。

| 建议关系记录 | 关键字段/关系 | 必须可验证的约束 |
| --- | --- | --- |
| `iam.principals`、`resource_grants` | 主体 ID、单一角色、活动标记；主体与资源 ID 的授权 | 角色限定三个批准角色；授权唯一；主体/资源外键完整；无授权默认拒绝 |
| `iam.authorization_revision`、`authorization_changes` | 单行全局修订；变更 ID、预览修订、操作者、原因和前后差异 | 修订非负且只递增；变更 ID 唯一；同 ID 不同内容拒绝；修改授权与审计同事务 |
| `presales.resources`、`resource_versions` | 资源类型、归属父资源；具体版本、来源类别、依赖完整性/就绪标记 | 实体共享资源 ID；依赖和 grants 引用真实资源外键；每个版本属于固定资源；原始来源有完整来源声明，派生来源有输入清单；空依赖不等于原始来源 |
| `opportunities`、`tasks` | 商机资源 ID；任务资源 ID、商机 FK、状态、行修订、输入集修订、候选版本 ID | 任务归属不可随编辑移动；候选必须属于本任务；空候选合法；首阶段任务只创建为“新建”，其他转换未接入时默认拒绝 |
| `materials`、`material_versions` | 商机或任务归属、来源/使用声明；资源版本 FK、逻辑文件键、摘要、大小、就绪关联 | 每份材料恰有一个归属；任务归属与商机一致；内容版本不可覆盖；拒绝真实客户敏感材料声明，来源不明保持待补充、不开放读取 |
| `proposal_versions`、`proposal_revisions` | 任务 FK、版本序号、生命周期、当前修订；正文 JSONB、schema_version、编辑者 | `(task_id, version_no)` 和 `(version_id, revision_no)` 唯一；当前修订属于同版本；旧正文只插入不更新；仅草稿/需修改可保存新修订 |
| `direct_dependencies` | 下游资源版本、上游资源版本、依赖用途 | 双向外键、边唯一、不得自环或成环；输入依赖完整；正文引用是依赖的子集，不能替代依赖清单 |
| `file_readiness`、`command_receipts` | 文件核验意图/状态；请求 ID、actor、操作、目标、固定参数、结果引用 | 文件键和内容版本唯一；请求身份不混同关联日志 ID；同请求同参数返回原结果，同请求异参拒绝 |
| `audit.events` | 事件 ID、actor/本机操作员、动作、目标、修订、结果、请求及授权修订 | 运行/维护身份只追加及受控读取，不能更新/删除；业务成功与审计同事务；客户正文及秘密不写入 |

首阶段只形成草稿的结构化存取契约：`schema_version` 从 `1.0` 开始，保存 identity、provenance、access 和未完成区块的明确标记；不伪造 Analysis Attempt 或完整分析结果。完整 P06 Schema、Evidence Snapshot 聚合及其必需门禁在阶段二、三形成；首阶段的来源版本和定位外键为其基础，不能把草稿存储校验称为完整 Proposal Package 校验。Review/Approval、发布动作及运行表不提前创建空壳。

Opportunity 由显式演示种子/本地初始化登记，运行时本阶段仅在已授权商机下创建任务；不据此新增“任意用户创建商机”的权限。没有运行中分析的阶段一仍保存完整 P01 状态值，但公共服务仅开放本节列明的创建、草稿读取和编辑，不提供任意 `set_status`。

### 3.6 授权检查路径

JWT 验证组件检查签名、issuer、audience 和有效期，只提取稳定 subject，后续由 FastAPI 依赖适配。应用服务读取数据库当前活动状态、唯一角色、操作能力、资源授权、对象状态及修订；不接受请求自报的 `user_id` 作为身份。Opportunity 授权仅向下覆盖其任务和材料；Task 授权限定本任务及其材料；共享知识独立授权。派生物读检查同时覆盖对象归属和所有直接来源依赖的递归闭包；缺来源、循环或未知权限时拒绝整个结果。

授权维护预览绑定全局单调递增的授权修订。应用时短事务比对预览修订、更新授权、递增版本并追加审计；旧预览拒绝。普通业务连接不可更新授权。用户登录与 JWT 签发界面不在本阶段交付，账号口令不得持久化；签发方案在阶段二 API 开放前设计，不保留无认证的业务入口。

### 3.7 写入、读取与撤权的事务顺序

这是作者给出的首版工程默认协议，接受阶段方案后按此编制任务：

1. 身份验证在事务外完成；进入短事务后获取固定授权锁键的 `pg_advisory_xact_lock_shared`，随后读取当前主体及权限。所有初始化/授权维护写入必须先取同键的排他 `pg_advisory_xact_lock`，再锁定并条件更新授权修订记录；成功提交是撤权生效顺序点。业务角色不对 IAM 使用 `SELECT FOR SHARE`，也不因加锁而获得 IAM 的 UPDATE 权限。业务提交在撤权之前则属于先前已授权操作，之后的新操作必须拒绝；锁随事务释放，不跨文件、模型或 HTTP 等待。
2. 当前身份、角色能力及目标/来源权限通过后，先按 actor、操作和请求 ID 查询 `command_receipts`。若已有回执，固定参数相同则返回受当前权限约束的原结果引用，即使原 expected revision 已过期也不再次执行；参数不同则拒绝。撤权后不能通过回执读取旧受限内容。并发同请求先按独立请求锁键串行，避免两个请求同时查询不到回执。
3. 仅对没有回执的新请求，验证操作角色（创建任务须架构师及商机范围）、业务状态，再按固定顺序锁定 Task、Proposal Version，检查预期行修订和预期内容修订。若不匹配则整体回滚；匹配后同事务追加正文修订、直接依赖、更新候选/当前指针、写入结果回执及审计。独立请求基于同一预期修订只能一个成功；此请求 ID 不是 TD-030 的 MCP 批准动作 ID。
4. 来源边在事务内验证上游存在及当前可访问、原始声明或派生依赖完整、归属合法、无环。首版写依赖时取独立图锁键的事务级排他 advisory lock 后检查递归闭包，防止两事务各插一条边共同成环；新正文与依赖同事务提交。服务端输入清单生成依赖，客户端不能仅按引用列表提交依赖；编辑既有正文时将上一修订及新增实际输入作为直接依赖，删除显示引用不移除其来源限制。已就绪版本的依赖不可原地追加/删除，应建立新修订。
5. 读取在同一短事务内检查主体、对象归属和完整来源闭包，再物化授权结果；正文由持久层完成此路径后才返回。已撤权来源、缺边、循环、未就绪或未知来源均拒绝整个派生物。拒绝响应不带来源名称、片段或对象存在性线索；对外不存在与无权访问统一处理。
6. 业务成功审计原子提交；拒绝/回滚事件在回滚后单独追加最小审计。若审计存储不可用，受保护操作明确失败，不绕过审计继续。多余审计正文不能成为受限内容的旁路。

首版使用 PostgreSQL READ COMMITTED 配合上述锁和条件更新，不依赖 ORM 缓存授权。统一锁顺序为授权锁、请求锁、Task/Version 行锁、图锁；不同锁键命名空间固定并相互隔离，设置有限锁等待时间。advisory lock 是所有受控数据库写入路径遵守的协议，不宣称可约束任意高权限手工 SQL；维护角色凭据不得提供给普通运行进程。可重复物化的小对象读取锁不会覆盖后续离线文件下载；文件读取须在打开前及返回前重新验权，已完成的历史读取不能远程撤回。完整流式导出在后续阶段定义，不宣称事务锁能撤回已发送字节。

### 3.8 文件就绪与失败核实

先以短事务登记不可见记录及预期来源，再在受控目录写临时文件、计算摘要并原子替换到服务端生成的逻辑键；文件操作不持有数据库事务。随后重新鉴权，以短事务核对键、内容版本、大小/摘要、来源声明和依赖完整性，条件更新为可读并追加审计。存储适配器拒绝路径穿越和越出根目录的符号链接/重解析点，不把用户文件名拼成路径。

文件成功而 DB 回执失败时，按同一 readiness ID 核实文件及数据库记录，不创建第二份材料；文件缺失、损坏或来源不齐保持不可见，记录核实失败。显式恢复命令可重复核验待就绪记录，不自动开放旧文件；已有就绪文件读时发现损坏同样拒绝。首阶段不自动清理孤立文件和删除历史材料。

### 3.9 模块及服务契约

| 建议位置 | 职责/调用契约 |
| --- | --- |
| `src/presales/domain/` | 状态值、身份与归属、修订门禁、纯领域校验；不导入 FastAPI、模型或数据库连接 |
| `src/presales/application/` | `create_task`、`register_material`、`create_draft`、`save_draft`、`read_draft`、`read_material`；写命令接受可信 actor、目标、expected revision、请求 ID 和业务参数，返回 ID/新修订；读取统一授权 |
| `src/presales/infrastructure/` | SQLAlchemy 表映射/repository/UoW、本地文件适配、独立配置；repository 不对 Agent 或通用 API 暴露 |
| `src/presales/access/` | JWT verifier、主体解析、角色能力、有限继承和依赖闭包；签名算法显式白名单，issuer/audience/时限必验；组件单独可测 |
| `src/presales/maintenance/` | 显式初始化、`authorization preview/apply/status`、`readiness reconcile`；不在 Web/Agent 注册 |
| `migrations/`、`tests/presales/` | Alembic 版本与无模型单元/契约测试；PostgreSQL 集成测试单独标记并需要专用测试库配置 |

未预期修订、同请求异参、缺材料就绪、业务状态不允许等返回明确领域错误；认证缺失/无效与存储不可用分别表达。事务重试只对已判明的可重试数据库冲突执行有界重试；提交结果未知时先按原请求 ID 核实，不能直接再创建。

维护身份来自当前 OS 账户的可核验标识及本地允许列表，不接受任意 `--actor` 冒名。`preview` 输出变更 ID、基准授权修订及无秘密差异；`apply` 必须指向该预览、填写原因，扩权另有显式确认；`status` 在响应丢失时按原变更 ID 核实。初始化采用单次数据库标记，重跑只报告现状，不覆盖已撤销授权；需要补充对象走维护变更。不同连接身份不相互继承权限，权限 bootstrap 由专用配置步骤完成，普通服务不持有迁移/维护凭据。

| 风险/未决点 | 当前依据 | 处理方式 |
