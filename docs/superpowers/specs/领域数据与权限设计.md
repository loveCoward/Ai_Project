## 1. 范围和已确认前提

本专题负责对象关系、权威数据归属、内容修订、来源依赖、当前授权及业务写入一致性。尝试与 graph thread 的绑定及分析槽位见[工作流与发布恢复设计](工作流与发布恢复设计.md)；具体 API、LangGraph DAG、MCP 协议和环境运行步骤在各自专题展开。

本文保留方向确认时的背景及跨阶段约束；文中的“待设计”由对应阶段方案逐步细化，不表示已经细化的首阶段建议仍需重新访谈。首阶段具体建议和评审边界集中见上链方案。

已确认的前提：

- TD-003：一个 PostgreSQL 实例和数据库，业务、知识和工作流按 schema 分组。
- TD-004：Windows 原生开发，文件内容存放于可配置的受控本地目录，数据库保留关联元数据。
- TD-006：七组业务职责模块，跨模块操作由应用服务组织。
- TD-007：关系记录、JSONB 内容修订和追加审计分工；查询投影不另建可编辑事实源。
- TD-010：首版每个预置账号只绑定一个有效角色。
- TD-011：按用户和资源范围显式授权；无匹配授权时拒绝访问。
- TD-012：商机授权向下覆盖任务和客户材料；任务授权仅覆盖本任务及其客户材料；共享知识独立授权，不向上或横向继承。
- TD-013：JWT 标识身份，服务端读取当前角色与资源授权，不以旧 token 内权限替代当前检查。
- TD-014：使用不含秘密的预置配置初始化，数据库保存运行中的当前授权，通过受控本地维护命令更新并审计；重启不自动覆盖授权。
- TD-015：后台分析绑定已验证的发起人、任务、输入修订、允许范围和独立尝试；不保存浏览器 JWT，运行中持续检查当前权限及尝试状态。
- TD-016：每次尝试的授权范围取启动时范围与运行时当前授权的交集；后续扩权不扩大旧尝试。
- TD-017：授权失效后停止后续调度，部分结果仅保留在受来源限制的审计轨迹中，不写入当前候选方案；之后用新尝试继续。
- TD-018：本机可信操作员预览授权变更并明确应用，记录操作者、原因及前后值；扩权须额外明确确认。
- TD-019：整批授权变更与审计在短事务内原子提交；拒绝过期预览，响应丢失按变更标识核实。
- TD-020：保存直接输入依赖关系并追溯全部原始来源；正文引用单独记录，展开清单仅作为可重建投影，来源缺失或循环时拒绝访问。
- TD-021：来源依赖齐全并核验后，派生物才对业务读者可见；方案修订及其直接依赖同事务保存。
- TD-022：首版维护预览绑定单一全局授权修订序号，任一授权相关变更成功提交即递增；过期预览须重新查看差异。
- TD-023：日常服务连接只读授权关系；显式初始化和本地维护使用独立且受限的数据库写权限，审计绑定可核验的本机操作员。
- TD-024：业务数据库中的待就绪记录是跨存储派生物可见性的权威依据；重启核验全部条件后才幂等开放读取。

本专题遵守需求基线第2-6、8节的权限、状态、证据和审计要求。单租户不取消对象范围授权，schema 分组也不自动实现访问控制。

## 2. 业务对象关系：沿用需求，不新增批准

下表重述业务基线第3节及 GLOSSARY 的关系约束，用于确定设计对象，不是物理表清单。

| 对象或关系 | 必须保持的语义 |
| --- | --- |
| 商机与本地方案任务 | 一个商机可有多个任务；本地任务可先于外部任务记录存在 |
| 任务与 Proposal Analysis Attempt | 每次分析有独立尝试身份和历史，重跑不能覆盖旧尝试 |
| 任务与 Proposal Version | 任务可产生多个版本；版本、尝试和聊天线程身份不得混用 |
| 方案版本与内容修订 | 草稿编辑递增内容修订，提交绑定固定修订；批准的正式正文不可覆盖 |
| 证据与 Evidence Snapshot | 引用稳定来源身份及版本和定位；历史依据保留但读取受当前授权约束 |
| Review Record 与 Approval Record | 审阅评论和授权决定分别表达；批准绑定对象快照及明确动作集合 |
| Approved Action Set 与逐项结果 | 完整动作集合逐项记录成功、失败或未知，全部成功才能发布完成 |
| Long-term Memory | 确认程度与有效性分别表达，只有符合业务条件的陈述可作为确定事实复用 |

对象状态和允许的转换以需求基线第4节为准；物理字段、枚举编码、外键及唯一性约束尚待设计。

## 3. 权威数据分工：TD-007 已确认

| 信息 | 权威保存位置 | 与其他表示的关系 |
| --- | --- | --- |
| 对象身份、归属及当前业务状态 | 关系记录 | JSON 导出中的对应标识应与所选对象及修订一致，不能反向作为状态变更命令 |
| 方案内容修订 | 指定修订的 JSONB 快照 | 需求分析、覆盖结论、方案正文、证据引用、风险和澄清内容以该快照为准 |
| 来源身份、版本及权限依赖 | 关系记录 | TD-020 以直接输入依赖为权威并追溯完整闭包；正文引用单独记录并匹配对应修订，当前授权不由历史 JSON 决定 |
| 审阅、批准、风险接受和动作集合 | 对应业务关系记录及审计 | 绑定所审修订与对象，导出封套反映相关记录；不得随意改写已批准事实 |
| 发布动作结果与核实历史 | 对应关系记录及追加审计 | 不更新批准正文；具体当前结果与历史事件的事务关系待细化 |
| 正文查询索引或投影 | 可由快照生成的派生表示 | 不独立接受正文编辑；修订错配或投影滞后的处理需在实现设计中明确 |
| 原始文件及保存的导出文件 | 受控文件目录 | 数据库保留存储键、版本、来源及校验关联；路径不充当业务身份，派生文件可见性以 TD-024 的业务记录为准 |
| 图执行 checkpoint | 工作流存储 | 服务执行恢复，不替代正式业务记录或当前权限判断 |

正文中的风险分析与审核人的风险接受决定具有不同职责；澄清依据也须保留来源及身份关联。详细模型必须逐字段区分业务对象、某修订中的评价和追加治理记录，不能因为都能装进 JSON 而混为同一份可变数据。具体拆分待确认。

## 4. 保存、提交和导出约束

已确认的保存方向及已批准的业务约束如下：

1. 保存草稿形成新内容修订，保留原修订和操作者。重复请求如何判定为同一次保存，仍需定义幂等规则。
2. 提交固定内容修订和证据快照；待审阅期间不能直接编辑，须先按基线撤回并失效旧请求。
3. 批准绑定当前有效的提交快照、风险接受和指定动作集合；已批准正文和证据快照不可覆盖。
4. 发布过程追加结果和审计封套，不因失败、恢复或完成改变批准正文。
5. JSON、Markdown 和 HTML 针对同一指定内容修订生成，显示审计封套的生成时间及对应状态。
6. 旧尝试、取消尝试和失效审批不得覆盖当前候选版本或触发新的外部副作用。

TD-009 已确认通过预期修订校验和短事务拒绝过期操作；具体事务边界、条件更新和审计一致性尚待设计和测试。内容摘要的规范化和摘要范围、JSON Schema 版本升级策略也待细化。

## 5. 权限需求与待确认实现

### 5.1 已批准要求

依据需求第2节和 P02，每次操作检查身份、角色、当前对象范围与业务状态。派生物需同时满足归属对象和所有实际输入来源的访问权限；不能只按最终引用计算。未知来源或权限缺失时拒绝。来源限制覆盖方案、导出、记忆、缓存、轨迹及 MCP 正式记录。

权限收紧影响后续访问和恢复；历史快照不能恢复已撤销的权限。向量与关键词两路检索均需在形成受限候选和上下文前过滤。角色允许审阅不等于拥有全部来源权限，审批不能扩大读者范围。

### 5.2 已确认机制方向，数据模型待设计

- 用户已确认通过统一授权组件和显式对象/来源依赖关系实施后端检查。JWT 提供可验证主体；服务端校验当前角色和数据授权。
- 已确认权限检查覆盖实际输入来源闭包，并将依赖关系与对应修订或产物关联。处理阶段、缓存和图状态的来源归属也须设计，不能只保护最终成品。
- 首版不要求增加数据库行级安全（RLS）作为额外防线。数据库角色权限、访问策略及未来是否额外采用 RLS 仍待设计；schema 分组本身不是权限校验，也不是安全测试通过证据。

权限关系表、用户角色来源、当前授权的失效策略、权限变更与在途操作的竞争、结果不泄露的拒绝响应、MCP 身份传递及来源完整性校验尚待设计。

**TD-013 已确认：** JWT 携带稳定用户身份及必要的签发者、受众、有效期等校验信息；服务端在每个受保护操作中读取当前有效角色和资源授权。请求中的 `user_id` 或 token 内缓存的权限不作为当前授权来源。授权撤销后新请求按当前记录拒绝，不等待 token 自然过期。token 具体时限、账户停用、强制失效和凭证保存仍待细化；授权初始化和更新入口按 TD-014，后台分析身份和生命周期按 TD-015 处理。

用户已确认 TD-010/TD-011：角色决定操作类别，对象授权决定可访问资源；三个预置账号各绑定一个有效角色，资源访问按用户与授权范围判断，未匹配默认拒绝。TD-014 已确认预置配置、数据库当前授权及本地维护命令的责任分工；具体配置格式、关系约束、命令契约和审计字段仍需设计。

用户已确认 TD-012 的有限继承：商机授权可用于其下属任务及客户材料；任务授权不扩大到父商机或兄弟任务；共享知识版本独立授权。此继承只确定业务对象范围，不替代派生物对归属对象和所有实际来源进行逐项授权交集检查。父子关系、删除/移动约束和权限撤销生效策略仍待细化。

### 5.3 TD-014：配置初始化，数据库保存当前授权

状态：设计方向已确认。确认日期：2026-11-02。Round 9 Q14 用户回复“我同意”。

预置配置描述不含秘密的用户身份、单一角色、状态及资源授权，首次通过显式初始化导入关系表；运行时查询数据库中的当前授权。后续由可信本机操作员通过受控维护命令校验、展示差异并显式应用变更，同时记录操作员、原因、时间和前后值；权限放宽时要求额外的明确确认。该维护入口不新增业务管理员角色或 ACL 管理控制台，不由模型或普通业务请求调用，也不要求第二人复核。

服务重启不得以种子配置自动覆盖当前授权，避免恢复已经撤销的权限。密码、签名密钥和 token 不写入种子数据、业务关系表或日志；维护连接与日常服务连接按 TD-023 隔离。账号验证、配置格式、维护命令契约、更新并发和失败恢复细节仍待设计；此处只记录机制，不创建命令、配置或数据。

备选是每次授权读取本地配置，但需另外处理多进程配置可见性、更新一致性及变更审计。当前选择数据库保存运行中的授权。

### 5.4 TD-015：后台分析绑定发起人和执行尝试

状态：设计方向已确认。确认日期：2026-11-02。Round 9 Q15 用户回复“我同意”。
关联决策：[ADR-0001](../../adr/0001-background-analysis-authorization.md)。

由已经鉴权的启动操作在服务端创建分析尝试，记录发起人、任务、输入修订和本次允许的分析范围。后台执行只能通过可信的运行记录取得该上下文，不能仅凭调用方自报的用户身份执行；节点读取、检索和对外服务调用前按发起人的当前权限重新检查，并遵守尝试状态、取消标记和运行预算。登录 JWT 不写入图状态、持久化任务或日志。

已经合法启动的分析不因浏览器访问 token 自然过期而自动中止；后续交互、人工审批和重启恢复仍须新的有效身份校验。账户停用、授权撤销、任务取消或尝试失效时阻止后续受限操作；授权失效的访问范围和部分结果处置按 TD-016/TD-017 执行。

审批与发布采用各自已批准的动作及审核人授权规则，不借用分析发起人的身份完成审批或外部写入；可信执行上下文也不是可任意复用的授权凭证。内部进程/MCP 的身份认证、范围绑定和防伪造协议仍待设计。

备选是让分析执行绑定浏览器访问 token 的存续期，到期即暂停并等待重新认证。当前选择解耦入口 token 与合法分析尝试的寿命，同时保留当前权限检查；范围扩张仅由新尝试承载。

### 5.5 TD-016：尝试范围与当前授权取交集

状态：设计方向已确认。确认日期：2026-11-02。Round 10 Q16 用户回复“同意”。

启动时记录的任务、输入修订和允许来源限定本次 Proposal Analysis Attempt 的范围上限。每次受限读取、检索和外部服务调用还须通过当前授权检查。运行期间新增授权不会扩大旧尝试，撤销授权立即缩小可用范围；使用新授权来源或输入修订须创建新尝试。该规则落实 P02 的当前授权复核，不改变业务状态机。

授权范围的具体快照字段、来源依赖闭包的精确校验位置，以及权限变更与已发出调用的竞争处理仍待设计。

### 5.6 TD-017：授权失效后停止调度并隔离部分结果

状态：设计方向已确认。确认日期：2026-11-02。Round 10 Q17 用户回复“同意”。

当前授权或尝试状态不允许下一受限步骤时，停止后续调度。已发出的调用不能撤回；其返回内容在任何进一步处理或写回前须重新验权。部分分析结果和轨迹保留在原尝试的审计记录中，并继续受全部实际来源的当前访问权限限制；不得写入当前候选方案或作为正式分析结果使用。尝试因权限失效结束后，即便授权之后恢复，也以新 Proposal Analysis Attempt 开始后续工作。

任务取消仍按已批准的任务状态转换处理。尝试级终止原因、部分记录的保留形式、不可见结果的审计边界及 checkpoint 停止协议仍待细化。

### 5.7 TD-018：本地操作员显式应用授权变更

状态：设计方向已确认。确认日期：2026-11-02。Round 10 Q18 用户回复“同意”。

授权维护命令由可信本机操作员发起，先展示完整变更差异，再显式应用。审计记录操作员身份、变更原因和变更前后值；扩权须有额外明确确认。首版不另设业务管理员角色或第二人复核流程。

TD-019 已确认整批变更及审计原子提交、拒绝过期预览和响应丢失后按变更标识核实。TD-022 已确认授权修订采用全局递增序号，TD-023 已确认使用可核验的本机操作员身份和独立维护权限；具体身份映射、命令变更集格式及并发控制写法仍待设计。

### 5.8 TD-019：授权变更与审计原子提交

状态：设计方向已确认。确认日期：2026-11-02。Round 11 Q19 用户回复“同意”。

一次维护命令提交明确的变更集，绑定预览时的授权修订。应用时在短事务内重新检查修订，写入该批授权变更、递增授权修订并追加审计；任一项失败则整批不提交。预览后出现其他变更时拒绝旧变更集并要求重新预览，不自动覆盖。已完成的命令遇到响应丢失时，通过本次变更标识核对结果，不重复应用。

相较逐项提交，整批提交避免出现“部分授权已变化、审计或其他项失败”的中间结果。授权修订粒度见 TD-022；具体命令格式、操作员身份验证、变更标识和冲突响应仍待细化；尚未实现。

### 5.9 TD-020：直接来源关系与完整依赖闭包

状态：设计方向已确认。确认日期：2026-11-02。Round 11 Q20 用户回复“同意”。
关联决策：[ADR-0002](../../adr/0002-direct-source-dependencies.md)。

关系记录保存每份节点结果、方案修订、导出和记忆的直接输入依赖，访问时沿这些关系解析全部原始来源，并检查当前授权。最终正文的引用集合单独保存，用于论断证据展示；删掉显式引用不能删除实际输入依赖。来源链无法解析或出现循环时拒绝访问，不把不完整依赖当作没有限制。

例如节点 A 使用安全资料 S1，节点 B 使用产品资料 S2，汇总方案使用 A 和 B；即便正文只引用 S2，整个方案仍受 S1 和 S2 共同限制。备选是每份产物只保存展开后的完整来源清单：查询简单，但更难解释中间结果如何继承限制。当前选择以直接关系为权威，展开清单仅作为可重建的查询投影。具体关系表、不可变修订绑定、产物与依赖一致提交及投影一致性仍待设计；尚未实现。

### 5.10 TD-021：产物及来源依赖同时就绪

状态：设计方向已确认。确认日期：2026-11-02。Round 12 Q21 用户回复“同意”。

方案内容修订和该修订的直接来源关系在同一短事务中写入，只有来源链完整、无循环并通过归属检查后，修订才能供业务读取或提交。节点结果、导出文件或记忆若跨 checkpoint/文件等不同存储，先作为内部待就绪记录；其权威来源关系持久化并核验后才对业务读者可见。失败时保留受限、可审计的未完成记录，不公开缺少来源关系的正文。编辑方案创建新修订及其独立依赖，不能原地改写已批准修订的依赖。

备选是先让产物可见，再异步补来源关系；这会形成短暂的越权窗口。已确认的就绪门禁只决定内部可见性，不新增任务或方案版本的业务状态。跨存储恢复的权威依据按 TD-024，具体扫描和清理规则仍待细化。

### 5.11 TD-022：首版使用单一授权修订序号

状态：设计方向已确认。确认日期：2026-11-02。Round 12 Q22 用户回复“同意”。

本地授权维护命令的预览绑定一个全局递增的授权修订序号；任何账号状态、角色或资源授权变更成功提交都会递增。应用变更时若修订不相同，就拒绝旧预览并重新生成差异。首版只有三个账号、受控本地维护入口，接受不同账号变更之间的额外重试，以避免细粒度版本遗漏跨对象、继承或角色变化。该序号不替代运行时读取当前授权。

备选是每用户/资源独立修订以减少冲突，但维护命令涉及多个对象时要同时比对若干版本。具体物理约束、变更标识和授权读取性能仍待设计；尚未实现。

### 5.12 TD-023：本地维护使用独立数据库写权限

状态：设计方向已确认。确认日期：2026-11-02。Round 13 Q23 用户回复“同意”。关联决策：[ADR-0003](../../adr/0003-separate-authorization-maintenance-privileges.md)。

普通业务服务的数据库连接可读取当前授权记录，但不能直接修改账号状态、角色和资源授权关系；显式初始化及受控本地维护命令使用单独、限于授权维护对象的数据库写权限。命令只从受控本机账户启动，审计绑定可核验的本机操作员身份和命令变更标识，不信任命令参数中自报的操作员姓名。维护凭据按本地秘密管理，不能写入种子配置或日志。

备选是命令与业务服务共用数据库写权限、只靠应用入口约束，配置更少，但服务进程持有修改授权的能力。独立权限会增加连接凭据和迁移管理成本；具体本机身份映射、数据库角色与审计写入权限仍待设计。不增加数据库 RLS 或业务管理员角色。

### 5.13 TD-024：跨存储待就绪记录以业务记录为恢复依据

状态：设计方向已确认。确认日期：2026-11-02。Round 13 Q24 用户回复“同意”。

业务数据库保存派生物的待就绪标识、存储键、修订、权威来源关系及核验结果，作为是否可被业务读取的权威依据。重启后按未完成记录核对文件或 checkpoint 是否存在、版本与校验值是否匹配、来源链、当前授权与尝试是否仍有效；仅在全部检查通过时幂等地标为可见。内容缺失、依赖不完整、尝试失效或结果不确定时保持受限的待恢复记录，报告原因并留给受控恢复流程处理，不凭文件存在就自动开放。

备选是重启后依赖文件目录或 checkpoint 自动重建业务可见状态，步骤少，但难以确认内容修订与来源关系已经一致提交。此处的产物核对不等于自动恢复图执行；继续交互、审批或图恢复仍遵守 TD-015 的重新鉴权要求。具体扫描时机、恢复触发权限、清理及长时间未完成记录的处置仍待设计。

## 6. 过期操作与一致性：机制方向已确认

用户已确认：保存、提交、批准和分析结果回写采用修订或状态校验，在短数据库事务内提交所需业务写入；过期操作被拒绝。具体数据库约束、条件更新、事务边界及必要锁仍待细化和测试。旧尝试、取消标记和输入快照须一并核对。
