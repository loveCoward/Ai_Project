# 开发流程（方案 B）：分级、角色隔离与证据门禁

## 0. 文档状态

- 文档版本：v0.1-draft。
- 状态：方案 B 的流程定义，准备在后续任务中试点。在本文件被 `AGENTS.md` 引用、并由 CI/评审模板实际执行前，不构成本仓库的强制门禁。
- 目的：把“计划、实现、判断”从同一个长会话里拆开，使每个任务的完成状态都能由可复核的工件和命令证明。
- 范围：适用于本仓库后续的功能、缺陷修复、重构、数据迁移、权限、并发/恢复、外部集成和前端改动。
- 不替代：`AGENTS.md`、`CLAUDE.md`、需求基线、`GLOSSARY.md` 和已批准的实施计划。本文件只定义开发流程；需求内容、业务规则和阶段验收仍以原批准文档为准。
- 与现有证据分层的关系：本文的 L1/L2/L3 是**流程档位**；交付记录中的 A/B/C 是**证据环境层级**。二者正交，不能把“L2”理解成“只需要离线证据”，也不能把“A 层通过”理解成“流程已验收”。

## 1. 要解决的问题

当前流程的主要风险不是规则数量不足，而是规则没有变成执行结构：

1. 规划者、实现者和判断者处在同一个上下文里，验证容易退化为对已有实现的追认。
2. 一个阶段提交包含大量文件和行数，导致 diff 无法逐行审查，也无法二分定位和单点回滚。
3. 测试数量不能证明测试先于实现；没有 red 证据时，无法区分“测试验证需求”和“测试追认代码”。
4. 所有任务使用同一套流程，缺少轻量通道、风险升级、预算和停止条件。

方案 B 的基本单位不是“阶段”，而是一个**可独立审查的任务包**：

> 一个冻结的任务包 + 一次可证明的先红 + 一次独立验证 + 一个可回滚的合并。

## 2. 核心原则

1. **契约先于实现**：任务范围、验收条件、允许路径和停止条件在写代码前冻结。
2. **测试先于实现**：L2/L3 任务必须先有预期失败的测试，并保留失败证据。
3. **裁判不执行**：验证者不参与实现，也不修改代码和验收测试。
4. **提交按审查单元切分**：一个提交只表达一个意图，不按阶段打包。
5. **证据先于叙述**：命令、退出码、日志、SHA 和 diff 比“已完成”的文字结论可靠。
6. **状态只由集成者更新**：实现者不能自行把任务标成完成，也不能自行更新 `STATUS.md`。
7. **失败有边界**：连续失败、超预算、缺少真实环境或出现高风险变更时必须停止并升级，不能无限重试。

## 3. 任务生命周期

```text
DRAFT
  -> READY
  -> RED
  -> GREEN
  -> REVIEW
  -> PASS
  -> MERGED

任一阶段 -> BLOCKED
REVIEW -> CHANGES_REQUESTED -> GREEN
```

状态含义：

| 状态 | 含义 | 谁能推进 |
| --- | --- | --- |
| DRAFT | 正在拆分任务、识别风险和确定档位 | 规划者 |
| READY | 任务包和 AC 已冻结，允许写失败测试 | 规划者/人类 |
| RED | 失败测试已提交，且失败原因符合预期 | 测试作者 |
| GREEN | 实现使目标测试通过，等待独立验证 | 实现者 |
| REVIEW | 验证者正在只读审查和复跑 | 验证者 |
| PASS | 验证者给出 PASS，等待集成 | 验证者 |
| MERGED | 已合并，交付记录和状态已更新 | 集成者 |
| CHANGES_REQUESTED | 有可修复问题，退回实现者 | 验证者 |
| BLOCKED | 缺少环境、授权、AC 不清或连续失败 | 验证者/人类 |

RED 是一个证据状态，不要求整个分支始终处于失败状态。red commit 可以保留在任务分支历史中；PR 的合并门禁只检查最终 head。

## 4. 角色与隔离

### 4.1 角色表

| 角色 | 主要职责 | 可以写 | 不可以做 | 主要产出 |
| --- | --- | --- | --- | --- |
| 规划者 Planner | 拆分任务、冻结 AC、确定档位和预算 | `TASK.md`、设计/计划文档 | 修改 `src/`、验收测试或实现 | 任务包、AC 矩阵、风险清单 |
| 测试作者 Test Author | 把 AC 变成可执行断言，先制造 red | `tests/`、fixtures、测试数据 | 修改 `src/`，或按实现反推测试 | 失败测试、`RED.log` |
| 实现者 Implementer | 在任务包范围内让测试通过 | `src/`、必要的非验收测试 | 修改冻结的验收测试、扩大范围 | 实现提交、自检日志 |
| 验证者 Verifier | 独立复跑、检查证据和 diff，给出结论 | `REVIEW.md` | 修改代码、测试、任务包或状态文档 | PASS/CHANGES_REQUESTED/BLOCKED |
| 集成者 Integrator | 合并、更新状态和交付记录 | 合并提交、`STATUS.md`、`DELIVERY.md` | 修改业务代码或替实现者修 bug | 合并 SHA、状态更新 |
| 人类决策者 | 批准 L3、裁决范围/规则变化、接受残余风险 | 批准记录、决策记录 | 代替验证者伪造证据 | 明确决定和签署 |

### 4.2 隔离规则

1. **验证者不得是实现者**。L2 至少使用新的会话/工位；L3 使用不同模型实例或独立 agent，并由人类做最终确认。
2. **L2 的测试作者和实现者必须是不同会话**。测试作者只拿到 AC、接口边界和允许路径，不读取实现代码。
3. **L3 的规划、测试、实现、验证原则上分开**；如果项目规模不允许，至少保证测试作者、实现者、验证者三者不重合，并在 `TASK.md` 记录例外。
4. **验证者只读**。验证者发现问题后退回实现者，不直接改一行代码；验证者一旦修改代码，就必须重新指定新的验证者。
5. **交接通过文件，不通过聊天记忆**。实现者不能只口述“我修好了”，必须提交 `TASK.md`、`RED.log`、测试输出和 diff。
6. **集成者不是第二个实现者**。集成者只处理合并、状态和发布记录；修复应回到实现者。
7. **L3 禁止同一会话自我批准**。即使是同一模型的不同会话，也不能替代 L3 要求的人类确认。

## 5. 流程分级

### 5.1 档位定义

| 维度 | L1 轻量 | L2 标准 | L3 重流程 |
| --- | --- | --- | --- |
| 适用 | 文档、注释、格式、无运行时行为的维护 | 单模块/单页面行为；无公共契约、权限、持久化和外部写入 | 权限、数据/迁移、状态机、并发/恢复、外部写入、真实模型/浏览器、公共 API/契约、部署/回滚、跨模块共享代码 |
| 计划 | 简短任务便签 | 冻结的 `TASK.md` + AC 矩阵 | 设计/方案评审 + `TASK.md` + 人类批准 |
| 测试 | 不要求 red；运行相关文档/静态检查 | 每个 AC 至少一个 red test；测试作者与实现者分离 | 每个切片先 red；测试作者先审；真实环境矩阵 |
| 裁判 | 自检 + CI | 新会话独立验证 | 独立验证 + 不同模型/独立 agent + 人类确认 |
| 提交 | 1 个提交，最多 3 个文件 | 1—3 个提交；单提交最多 5 个文件、400 行净变更 | 按审查切片提交；每切片同样受 5 文件/400 行限制 |
| 预算 | 1 个实现轮次 | 2 个实现轮次 + 2 个验证轮次 | 每切片 2 个实现轮次 + 2 个验证轮次；超限升级人类 |
| 真实环境 | 不需要 | 按 `TASK.md` 声明，失败不能被 Fake 替代 | 明确列出 PostgreSQL、MCP、模型、浏览器等证据；缺一项即 `BLOCKED` |
| 完成 | 相关静态检查通过 | `REVIEW.md` PASS + CI 绿 | PASS + 真实证据 + 人类确认 + 合并/回滚记录 |

### 5.2 档位判定

先看是否触碰高风险路径，再看变更是否产生可观察行为：

- **L1**：只改文档、注释、格式、链接或纯排版；不改变可执行行为，不新增业务文件。任何 `src/`、`frontend/src/`、`migrations/`、测试逻辑或运行时配置改动都会自动升为 L2 或 L3。
- **L2**：默认档位。单个模块或页面的行为变化，没有公共契约、权限、持久化、并发、外部写入或真实环境依赖。
- **L3**：命中任一触发项即升级；不确定时按 L3 处理。

### 5.3 L3 触发项

以下任一项出现即视为 L3：

- `access/`、JWT、授权策略、角色/来源过滤、越权边界。
- 数据库 schema、迁移、事务边界、checkpoint、幂等键、唯一约束。
- 任务/Attempt 状态机、取消、恢复、租约、心跳、并发、槽位、旧代次拒写。
- 外部写入、MCP 写工具、发布、审批、外部系统集成。
- 真实模型调用、真实 PostgreSQL、真实浏览器或真实 MCP 进程作为验收证据。
- 公共 API、DTO、机器 schema、前后端共享契约。
- 部署、回滚、凭据、日志脱敏、数据保留策略。
- 跨模块共享代码，或会改变其他阶段已交付行为的改动。
- 任务包无法在一个审查切片内解释清楚，或规划者/验证者对风险判断有分歧。

### 5.4 升级与降级

- 实现者或验证者发现新风险，可以单方面**升级**档位并暂停当前实现，记录触发原因。
- 降级只能由规划者在重新核对影响后作出，并写入 `TASK.md` 的变更记录；L3 降级需要人类确认。
- 需求、业务规则、验收标准或授权范围发生变化，不走档位降级，回到需求/方案变更流程。
- 已完成的旧任务不追溯改写；从下一个未开工任务开始适用。

### 5.5 初判示例

| 任务类型 | 初判 | 理由 |
| --- | --- | --- |
| 只改 README 链接或排版 | L1 | 无运行时行为 |
| 单个纯函数校验器、单个页面展示 | L2 | 单模块，无高风险边界 |
| 方案分析节点、覆盖计算、Reflection | L2 | 先按单模块处理；若改共享契约或真实链路则升 L3 |
| Attempt 持久化、checkpoint、取消/恢复、并发验证 | L3 | 事务、状态机和旧代次风险 |
| `access/`、迁移、真实 PostgreSQL/MCP、真实模型/浏览器 | L3 | 权限、数据或真实环境 |

## 6. 任务包

### 6.1 必填内容

每个 L2/L3 任务在开工前必须有 `TASK.md`，至少包含：

| 字段 | 要求 |
| --- | --- |
| `task_id` | 稳定的任务编号，例如 `2B-2/T18` |
| `tier` | L1/L2/L3；填写判定理由 |
| `status` | 当前生命周期状态 |
| `base_sha` | 任务开始时的工作区基线 |
| `spec_refs` | 需求、方案、计划的准确路径和版本/章节 |
| `goal` | 一句话说明用户可观察的结果 |
| `non_goals` | 明确不做什么，防止顺手扩范围 |
| `allowed_paths` | 允许修改的路径或 glob；越界即验证失败 |
| `forbidden_paths` | 明确禁止修改的需求、规则、状态或其他任务文件 |
| `ac` | 验收条件矩阵，一行一个可观察断言 |
| `test_plan` | 测试文件、测试名、red 命令、green 命令 |
| `real_env` | PostgreSQL/MCP/模型/浏览器等环境及证据要求 |
| `budget` | 最大文件数、净变更行数、提交数、实现/验证轮次 |
| `stop_conditions` | 本任务特有的停止条件 |
| `rollback` | 失败时如何回滚；是否可安全 revert |
| `roles` | 规划、测试、实现、验证、集成的角色分配 |

`TASK.md` 由规划者冻结。实现开始后，`goal`、`ac`、`allowed_paths` 和 `non_goals` 的变更必须回到规划者；实现者和测试作者不能自行放宽。

### 6.2 AC 写法

AC 不是一句“支持某某功能”，而是一条可以被测试判定的行为：

| 编号 | 可观察断言 | 测试 | red 命令 | 通过标准 |
| --- | --- | --- | --- | --- |
| AC07-a | 缺少关键结构时返回明确失败，不生成完整方案 | `test_missing_structure_fails` | `uv run pytest tests/...::test_missing_structure_fails -q` | red 时因缺少校验失败；green 时返回约定错误 |
| AC07-b | 无权限读取返回拒绝，且响应不泄漏正文 | `test_access_denied_does_not_leak_text` | 同上 | red 时越权读取成功；green 时拒绝 |

规则：

1. 一行只表达一个断言；不要继续使用 `AC07—10/21/27` 这种打包写法作为测试粒度。
2. 每个 AC 至少映射一个测试；一个测试只能主要服务一个 AC，避免“一个测试证明所有事情”。
3. 正向、负向、权限、失败、空结果、恢复/重试等行为要分开列。
4. 测试必须通过公共接口或契约边界断言，不能只验证私有实现细节。
5. 如果原需求 AC 很宽，可增加 `AC07-a`、`AC07-b` 子编号，但必须保留原 AC 引用，不能改写需求含义。
6. 不能自动化的验收项必须在 `TASK.md` 标记为人工检查，并写明检查人、步骤和证据；人工检查不能伪装成自动化测试。

## 7. 先红证据

### 7.1 Red 流程

1. 从 `base_sha` 创建任务分支和干净工作区；先记录基线测试状态。
2. 测试作者只写测试或测试夹具，不写生产实现。
3. 运行最小的目标测试，确认测试失败原因是**功能尚未实现**，不是导入错误、语法错误、fixture 缺失或测试环境错误。
4. 生成 `RED.log`，记录命令、退出码、失败测试名、预期失败原因和实际错误。
5. 只提交测试，提交信息以 `[RED]` 结尾。
6. 规划者或验证者先审 red tests：断言是否对应 AC、是否覆盖负例、是否测错边界、是否使用了不合理的 mock。
7. red tests 通过审查后才允许实现者写 `src/`。

### 7.2 RED.log 最小格式

```text
task: 2B-2/T18
tier: L2
base_sha: <sha>
test_commit: <sha>
test_file_sha256: <sha256>
command: uv run pytest tests/presales/test_example.py -q
exit_code: 1
collected: 12
passed: 0
failed: 2
failed_tests:
  - test_missing_structure_fails
    expected_failure: missing behavior
    actual: AssertionError: expected failure result
```

`RED.log` 不能只包含 collection error 或“0 tests collected”。如果测试文件本身无法被收集，先修复测试基础设施，不能把收集失败当作先红。

### 7.3 先红审查清单

- [ ] 测试对应 `TASK.md` 中的唯一 AC。
- [ ] 测试在 `base_sha` 上失败，且失败原因符合预期。
- [ ] 测试没有 `skip`、`xfail` 或无条件的“通过即跳过”。
- [ ] 没有把待测对象 mock 掉，也没有用实现细节替代行为断言。
- [ ] 负向、权限、空结果和失败路径至少覆盖 `TASK.md` 要求的范围。
- [ ] 测试文件 hash 和 red commit SHA 已记录。
- [ ] 测试作者没有读取实现代码后反向编写断言。

### 7.4 例外

- **L1** 不要求 red；只运行相关文档/静态检查。
- **纯重构** 可以先写 characterization tests，要求重构前后都通过；这不叫 red，不能用来冒充行为测试。
- **缺陷修复** 必须先写复现测试，证明它在 `base_sha` 上失败；回归测试不能只在修复后补写。
- **新测试基础设施** 可以把“建立可运行测试夹具”作为独立测试提交，但验收测试仍必须在生产实现前处于 red。
- **真实环境不可用**：保持 `BLOCKED`，不能用 SQLite、Fake transport、`typecheck` 或 `build` 替代真实 PostgreSQL/MCP/浏览器/模型证据。

## 8. 提交边界

### 8.1 分支和提交

- 分支：`task/<phase>-<id>-<slug>`，例如 `task/2b-2-18-solution-analysis`。
- 一个分支只对应一个任务；一个 PR 只对应一个任务包。
- 推荐提交序列：

```text
test(2b-2-18): add failing AC tests [RED]
feat(2b-2-18): implement solution analysis node
docs(2b-2-18): record red and green evidence
```

- 修复验证意见使用 `fix(<task-id>): ...`，不把修复和新功能混在同一提交。
- 重构使用 `refactor(<task-id>): ...`，要求重构前后测试都通过，并与行为变更分开。
- 一个提交只表达一个意图；格式化、清理、依赖升级不能搭便车。

### 8.2 大小门禁

默认限制（在试点中校准，不改变已有计划对任务总量的约定）：

| 检查项 | 默认值 | 处理 |
| --- | --- | --- |
| 单提交变更文件数 | ≤ 5 | 超过则拆成可独立审查的切片 |
| 单提交净变更行数 | ≤ 400 | 新增+删除，排除 lockfile 和已声明的生成文件 |
| L2 任务提交数 | 1—3 | 超过则检查是否任务过大 |
| 任务总净变更行数 | 参考现有计划的 300—800 行 | 超过 800 行先修订任务计划再拆分 |
| 生成文件 | 必须单独声明 | 记录生成命令、来源和校验方式，不能用来隐藏手写变更 |

这些是**审查粒度**限制，不是业务代码行数目标。一个任务可以有多个切片，但每个切片必须能独立验证；不能把一个大任务切成互相不完整的提交。

### 8.3 禁止事项

- 禁止“阶段级提交”：一个提交包含多个任务或多个独立能力。
- 禁止在同一个提交里同时包含 red tests 和实现代码。
- 禁止在实现提交中修改已经冻结的验收测试。
- 禁止删除失败测试、增加 `skip`/`xfail`、放宽断言来获得绿色。
- 禁止把用户已有的未提交修改混入任务提交。
- 禁止把格式化全仓库、无关清理或依赖升级夹带在功能提交中。
- 禁止直接向 `main` 推送；合并必须经过 PR 和门禁。

### 8.4 如果必须 squash

优先保留 red commit 历史。如果合并策略必须 squash：

1. 保存 `RED.json` 或 `RED.log`，包含 red commit SHA、测试文件 hash、命令和失败结果。
2. 在 `REVIEW.md` 记录“历史已 squash，red 证据由 artifact 保留”。
3. 由验证者核对 artifact 与最终测试文件一致；否则不能把任务标为 PASS。

## 9. 独立验证

### 9.1 Review bundle

验证者只接收以下材料，不读取实现者的聊天记录：

- 冻结的 `TASK.md`；
- `base_sha`、`head_sha`、分支名和 `git log --oneline base..head`；
- `git diff --stat`、`git diff --name-status` 和完整 diff；
- `RED.log`、测试文件 hash、red commit SHA；
- 实现者的自检日志和完整命令输出；
- 覆盖率报告；
- `real_env` 证据和环境版本；
- 已知缺口、未实现项和需要人类决定的问题。

### 9.2 验证者检查步骤

1. 在干净 worktree 检出 `head_sha`，确认 `git status --short` 为空。
2. 检查所有改动是否在 `allowed_paths` 内，是否有 forbidden 文件或无关格式化。
3. 对照 `TASK.md` 逐条检查 AC，确认每个 AC 有测试、测试在 red 阶段确实失败。
4. 检查 red 测试自 red commit 后是否被修改；如果改了，必须有规划者批准的变更记录。
5. 独立运行目标测试、全量测试、lint、类型检查和前端检查；L3 还要运行真实环境命令。
6. 做对抗性检查：越权、空结果、失败、超时、旧代次、重复调用、秘密泄漏、Fake 替代。
7. 检查是否新增 skip/xfail、删除失败样例、缩小断言或把错误吞掉。
8. 写 `REVIEW.md`，给出唯一结论和可复现命令。

验证者不得只看实现者的总结，也不得只依据 CI 绿色给出 PASS。CI 是必要条件，不是独立验证的替代品。

### 9.3 结论语义

| 结论 | 条件 | 后续 |
| --- | --- | --- |
| PASS | 所有 AC 有证据；diff 合规；red 证据有效；命令实际通过；无未解决的高风险缺口 | 交集成者合并 |
| CHANGES_REQUESTED | 有明确、可修复的实现或测试问题 | 退回实现者，修复后重新验证 |
| BLOCKED | 缺少真实环境、授权、依赖，AC 不清，或同一问题连续失败 | 停止实现，交规划者/人类处理 |

不允许“带条件 PASS”。如果存在未验证项，只能是 `BLOCKED` 或在人类明确接受残余风险后记录例外；例外必须写明影响和后续任务。

### 9.4 合并和状态

- 集成者确认 PR 模板、CI、`REVIEW.md` PASS、无未解决评论后合并。
- 合并后由集成者更新 `STATUS.md` 和 `DELIVERY.md`，记录 merge SHA、实际命令、测试数字、未实现项和证据边界。
- 实现者不能自行更新 `STATUS.md`，也不能把交付记录中的“建议完成”当成完成。
- 回滚使用 `git revert <merge-sha>`，并在交付记录中说明回滚原因和影响。

## 10. 停止条件与升级

| 条件 | 阈值 | 动作 | 负责人 |
| --- | --- | --- | --- |
| 无法产生符合预期的 red | 同一 AC 2 次尝试 | `BLOCKED`，重新检查 AC、测试夹具或接口契约 | 规划者 |
| 同一 AC 验证失败 | 连续 2 次 | `BLOCKED`，不再开第 3 次实现轮次，除非人类明确批准 | 验证者/人类 |
| L2 验证轮次用尽 | 2 轮 | 升级人类，判断拆任务或重定范围 | 验证者 |
| L3 单切片验证轮次用尽 | 2 轮 | 暂停该切片，升级人类；不得用放宽测试换通过 | 验证者/人类 |
| 单提交或任务超预算 | 首次发现 | 停止堆叠，拆任务/切片并重新冻结 | 规划者 |
| 发现新的 L3 触发项 | 立即 | 暂停，升 L3，补设计和批准 | 实现者/验证者 |
| 真实环境不可用 | 在需要证据前 | `BLOCKED`，不能用 Fake/build/typecheck 替代 | 验证者 |
| 测试被删除、skip/xfail 增加 | 任意一次 | 拒绝 PASS，记录原因 | 验证者 |
| 出现无关基线失败 | 任意一次 | 单独登记为既有问题；不得声称全量通过，也不在本任务顺手修复 | 验证者 |
| 上下文或预算接近上限 | 上下文约 70% 或 token 预算约 80% | 写 `HANDOFF.md`，换新会话，停止继续实现 | 所有角色 |
| 发现秘密或真实敏感数据 | 立即 | 停止、隔离、按安全流程处理 | 所有角色 |

停止不是失败的同义词。`BLOCKED` 是有证据的结论；继续尝试但不记录，才是失控。

## 11. CI 与自动化门禁

### 11.1 当前事实

当前 `.github/workflows/test.yml` 已运行 Python 测试、覆盖率采集、ruff、pyrefly、Markdown 检查和 Docker 集成；`codecov.yml` 的 patch coverage 仍为 informational，工作流没有 `--cov-fail-under`。仓库已新增 `scripts/task_gate.py` 和一个 `task-gate` CI job，但该 job 目前以 `advisory` 模式运行：没有任务包时只报告，不阻止合并。因此当前 CI 仍不能证明“流程门禁已强制落地”。

### 11.2 目标门禁

在试点通过后，PR 至少需要：

1. **任务门禁**：存在 `TASK.md`，档位、AC、允许路径、预算和 red 证据完整。
2. **提交门禁**：red commit 只含测试；实现提交不含冻结测试改动；单提交不超过文件/行数预算。
3. **测试门禁**：目标测试、全量测试、ruff、pyrefly、Markdown 和前端检查通过。
4. **覆盖率门禁**：项目覆盖率不低于已测量的基线，新增 patch coverage 达到约定阈值；不得用删除测试或新增 skip 提升数字。
5. **独立验证门禁**：`REVIEW.md` 存在且为 PASS；验证者身份不能与实现者相同。
6. **真实环境门禁**：L3 任务必须附带对应 PostgreSQL/MCP/模型/浏览器证据，不能用 Fake 或静态检查替代。
7. **分支保护**：`main` 只接受 PR；禁止直接推送；合并前必须有独立评审和必需状态检查。

`task_gate.py` 的当前检查范围：任务包必填字段、档位预算、`allowed_paths`/`forbidden_paths`、单提交文件/行数、red commit 只含测试、测试文件 hash 未变、reviewer 与 implementer 不同、AC 全部 PASS、L3 人工批准和真实环境证据。它**不执行**测试或真实环境命令，也不证明测试断言本身正确；这些仍由独立验证者复跑和审查。

覆盖率阈值先测量再固定：第一次试点记录当前基线和测试耗时，之后只升不降。具体数值属于试点配置，不在本文件中凭空指定；在数值写入 workflow 之前，不得对外宣称覆盖率门禁已启用。

`task_gate` 建议先实现为最小 Python 脚本，校验任务包、路径、提交范围和 red/review 工件；脚本本身也要有单元测试。不要先做一个无法测试的“大而全”平台。

## 12. 试点落地

### 12.1 顺序

1. **基线测量**：在干净工作区记录全量 pytest、覆盖率、前端检查、测试耗时和当前失败/跳过情况。
2. **L2 试点**：选择一个未开工的单模块任务（优先任务 18 一类的分析节点），完整走一遍任务包、red、实现、独立验证。
3. **L3 试点**：选择一个真实集成任务（例如任务 24 一类的真实 PostgreSQL/权限/恢复回归），验证真实环境矩阵和人类确认。
4. **自动化**：试点稳定后再加入 `task_gate.py`、PR 模板、覆盖率阈值和分支保护。
5. **制度化**：将 `AGENTS.md` 的“开始工作前/验证要求”链接到本文件，避免两份规则复制漂移；在 CI 真正执行前，不把本文件描述为已生效门禁。

### 12.2 试点指标

每个试点任务记录：

- red 证据是否完整，red 失败原因是否正确；
- 单提交文件数/行数分布；
- 验证者发现的问题数和类型；
- 实现/验证轮次；
- 是否有越权路径、测试改动或 Fake 替代；
- 合并后是否出现回归；
- 流程增加的实际时间成本。

不以“测试数量增加”或“覆盖率高”单独判定流程成功；核心指标是：判断是否独立、证据是否可复现、提交是否可审查、失败是否可停止。

### 12.3 不回写历史

已完成的阶段和任务保留原交付记录，不追认、不改写、不补造 red 证据。新流程从下一个未开工任务开始；对正在进行但尚未合并的任务，可以补建任务包，但必须明确标注“流程补建”，不能伪称当时已按此流程执行。

### 13.1 `TASK.md`

```markdown

- 状态：READY
- 基线 SHA：<sha>
- 依据：<需求/方案/计划路径与章节>
- 负责人：规划者 <name>；测试作者 <name>；实现者 <name>；验证者 <name>

## 目标

<一句话，用户可观察的结果>

## 不做什么

- <non-goal>

## 允许路径

- `<path-or-glob>`

## 禁止路径

- `<path>`

## 验收条件

| AC | 可观察断言 | 测试 | 命令 | 预期 red 失败 |
| --- | --- | --- | --- | --- |
| AC-01 | ... | `test_...` | `uv run pytest ...` | ... |

## 真实环境

| 环境 | 是否需要 | 证据 |
| --- | --- | --- |
| PostgreSQL | 否 | — |
| MCP | 否 | — |
| 真实模型 | 否 | — |
| 浏览器 | 否 | — |

## 预算

- 最大提交数：3
- 单提交最大文件数：5
- 单提交最大净变更行数：400
- 最大实现轮次：2
- 最大验证轮次：2

## 停止条件

- <task-specific stop condition>

## 回滚

<revert 策略和影响>
```

### 13.2 `REVIEW.md`

```markdown
# <task-id> 独立验证

- 结论：PASS | CHANGES_REQUESTED | BLOCKED
- base SHA：<sha>
- head SHA：<sha>
- 验证者：<name/独立会话>
- 验证时间：<date>

## 命令与结果

| 命令 | 退出码 | 结果 |
| --- | --- | --- |
| ... | ... | ... |

| AC | 结果 | 证据 |
| --- | --- | --- |
| AC-01 | PASS | 测试名/日志 |

- forbidden paths：通过/不通过
- red 测试是否被修改：否/是（说明）
- 新增 skip/xfail：无/有（说明）

## 发现的问题

- <问题、影响、要求修复的文件>

## 未验证项与风险

- <缺口；不得用“应该没问题”代替>
```

### 13.3 `DELIVERY.md`

```markdown
# <task-id> 交付记录

- 日期：<date>
- 档位：L2/L3
- merge SHA：<sha>
- 实际范围：<新增/修改/删除>
```

## 14. 待确认事项

以下事项在试点时必须由人类确认，不能由实现者自行决定：

- 当前仓库的覆盖率基线，以及项目覆盖率和 patch coverage 的具体阈值。
- L2/L3 单提交 5 文件/400 行是否适合本仓库的迁移、契约和测试文件规模。
- 独立验证使用哪种工位（新会话、不同模型、Orca worker 或人工评审）。
- 哪些历史任务需要在未开工前补建任务包，哪些保持原计划不变。
- 分支保护、PR 模板和 `task_gate` 的启用时间。
